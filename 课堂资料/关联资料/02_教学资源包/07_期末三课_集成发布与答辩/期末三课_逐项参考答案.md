# 期末三课：逐项参考答案与证据模板

这些是操作题，不是统一填空题。可照着完成动作和组织答案，但所有时间、网址、SHA、反馈和运行结果必须实际取得。未做的标“待验收”，不能复制“通过”。

## 第16课：集成发布

|步骤|具体在哪里做、写什么|合格答案的判据|
|---|---|---|
|1 检查单|工程根目录新建 release-check.md；逐项目填名称、URL、commit、检查命令、结果、负责人|P1—P5 都有一行，未完成项注明原因|
|2 入口检查|浏览器打开自己的门户并点每个项目链接；手机尺寸重做一次|正确到达目标，无横向溢出，能返回；后端不适用的项目明确注明|
|3 干净复现|新目录克隆实际待发布分支；按手册区分原生 P1 和 npm 工程|不借用原工程的 node_modules 和未提交文件|
|4 本地检查|P1 执行 node tools/check-page.mjs；其余先 npm run 查看脚本，再按项目手册运行|完整输出、退出码及执行时间；不存在的脚本写“不适用”|
|5 配置核对|检查 .env.example 和 git ls-files 输出，不展示真实 .env 内容|真实配置未跟踪，模板变量完整；发现泄漏先轮换密钥|
|6 发布与业务|部署个人测试地址，执行本课 smoke-test.mjs，再真实操作一次核心流程|HTTP 和业务结果分别记录；200 不等于业务正确|
|7 恢复演练|只在隔离副本使用已验证的备份/版本恢复流程|恢复后重复同一业务检查，数据仍可读；写清代码恢复和数据恢复区别|
|8 固定版本|新建 RELEASE_NOTES.md，写版本、时间、改动、验证和限制；全部必需项通过再创建标签|标签指向已验证提交；未完成不写“全部验收通过”|

## 第17课：产品答辩

工程根目录新建 product-defense.md，按下面顺序填写：

1. 用户与问题：用一段话写“谁、什么场景、当前困难、如何判断改善”，不要写“适合所有人”。
2. 三分钟任务：写页面入口→输入→操作→可见结果；例如音乐站选课堂合成音，搜索“练习曲”，播放并查看进度。
3. 三态演示表：正常输入“练习曲”；无匹配输入“无此曲目XYZ”；失败用开发者工具离线模拟网络请求，恢复在线后重试。按实际应用调整，不把空结果当网络错误。
4. 真实反馈：记录日期、脱敏用户、原话要点、采纳或拒绝、对应修改/理由。没有反馈写待收集，不能编造。
5. 证据索引：每个验收点对应自己的截图、网址或日志；只测地址就注明“仅 HTTP”。
6. 个人贡献：成员、实际提交、做出的取舍、下一版小目标；AI 建议必须说明自己如何验证。
7. 答辩记录：问题、未完成项、后续动作和负责人。提交上述文件，不能用教师示例代替真实演示。

## 第18课：工程答辩

工程根目录新建 engineering-defense.md，逐项填写：

1. 追溯链：自己的 Issue/任务编号、分支、提交 SHA、PR（如有）、发布标签；没有 PR 就如实说明。
2. 干净复现：克隆命令、分支、Node 版本、项目实际检查命令及完整输出。
3. 三类测试：正常、边界、失败各一个，记录预期与实际。P1 可用正常页面、手机窄屏、缺少 alt 属性。
4. 请求链：P1 是静态文件，无 API/数据库；其他项目记录页面动作→请求方法/路径→状态码→数据变化。不要伪造不存在的层。
5. 最小改动：新分支先写验收，再修复一个具体问题；不修改生产数据。
6. 防回归：重复触发原问题的步骤，保存修复前后结果；检查 diff 后提交，记录自己这次 CI。
7. AI 决策：采纳/拒绝哪条建议、理由、如何验证，不粘贴密钥和个人数据。
8. 恢复条件：什么现象需停止发布、使用哪份已验证备份、恢复后验证什么。HTTP 实验的固定 ok 响应不能当业务健康证据。

参考口述：“我在该提交改了这个文件，因为这个输入会触发这个错误；同条件测试从失败变为通过。线上验证覆盖这些步骤，尚未覆盖这些条件。”
