### 为什么不把昵称直接存在评论表里？

这是本课最值得想清楚的一个设计问题。

|做法|问题|
|---|---|
|❌ `comments` 表加一列 `author_name`|用户改了昵称，**过去所有评论还是旧名字**|
|✅ 只存 `user_id`，查的时候 JOIN 出昵称|昵称只有一份，改一次处处生效|

**同一份信息只应该有一个出处。** 这条原则叫"范式化"，
是关系型数据库设计的地基。项目 1 第 05 课那个"作品数据只写一份"是同一个道理。

> 反过来说，真实的大型系统有时会**故意**把昵称冗余一份，
> 目的是省掉 JOIN、查得更快。这叫"反范式化"。
> **但那是在遇到性能问题之后才做的取舍**，不是一开始就这么写。

### 一个最小例子：JOIN 在做什么

假设有两张表：

```text
comments                users
id  article_id user_id  body      id  display_name
1   3          2        写得好     1   张三
2   3          1        受教了     2   李四
```

只查 comments，你只能得到 `user_id = 2`——页面上显示一个数字。

```sql
SELECT c.body, u.display_name
FROM comments c
JOIN users u ON u.id = c.user_id
```

结果：

```text
body     display_name
写得好    李四
受教了    张三
```

**JOIN 就是"按这个条件把两张表的行配对起来"。**

**这一课要建立的核心观念**：

> **关系型数据库的价值不在于"能存东西"，而在于"能表达东西之间的关系"，
> 并且由数据库自己保证这些关系不会断。**

### TODO 01 · 评论表和它的两个外键

**难度**：极简单


**为什么做这个**
没有外键，`article_id` 和 `user_id` 只是两个普通数字。
可以写 `article_id = 99999`——指向一篇根本不存在的文章。
这种数据叫"**孤儿记录**"，查出来会报错，删不掉也用不了。

**涉及的知识点**

```sql
article_id INTEGER NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
user_id    INTEGER NOT NULL REFERENCES users(id),
body       TEXT NOT NULL CHECK(length(body) BETWEEN 1 AND 1000),
```

|部分|意思|
|---|---|
|`REFERENCES articles(id)`|这一列的值**必须在 articles 表的 id 里存在**|

这是个值得讨论的设计决定：

|如果用户被删|级联删除|不级联|
|---|---|---|
|他的评论|全部消失，别人的回复上下文断了|留着，但指向一个不存在的用户，**删用户这个操作会直接失败**|

### 已写好 · SQLite 的外键默认是关着的

**为什么做这个**
**这是本课最大的一个坑，也是最值得记住的一件事。**

你在 TODO 01 里写的 `REFERENCES` 和 `ON DELETE CASCADE`，
如果不打开这个开关，SQLite **一条都不会执行**——
建表语句照收不误、不报任何错，但运行时**完全不检查**。

很多人会花半小时怀疑自己外键写错了，其实语法完全正确，只是开关没开。

**涉及的知识点**

```js
database.exec('PRAGMA foreign_keys=ON; PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000')
```

|PRAGMA|作用|
|---|---|
|`foreign_keys=ON`|**打开外键检查**（本课重点）|
|`journal_mode=WAL`|读写并发更好：读的时候不挡写，写的时候不挡读|
|`busy_timeout=5000`|数据库被别人占用时，最多等 5 秒再报错，而不是立刻失败|

**`PRAGMA` 是"每个连接"的设置，不是存在数据库文件里的。**
所以每次建立连接都要重新执行一遍——这正是它写在建立连接那一步的原因。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 把评论和评论者连起来

**为什么做这个**
**这是本课视觉差别最大的一步。** 做之前评论区显示的是
`用户2 说：写得好`，做完之后是 `李四 说：写得好`。

**涉及的知识点**

```sql
SELECT c.id, c.user_id, c.body, c.created_at, u.display_name
FROM comments c
JOIN users u ON u.id = c.user_id
WHERE c.article_id = $1
ORDER BY c.id DESC
LIMIT 200
```

逐条看：

|部分|意思|
|---|---|
|`FROM comments c`|从 comments 表查，**给它起个别名叫 c**|
|`JOIN users u ON u.id = c.user_id`|按这个条件把 users 的行配对进来，别名 u|
|`SELECT c.body, u.display_name`|要 comments 的正文，也要 users 的昵称|
|`WHERE c.article_id = $1`|只要这篇文章的评论|
|`ORDER BY c.id DESC`|按编号倒序，**新评论排在前面**|
|`LIMIT 200`|最多 200 条|

**为什么要起别名？** 两张表都有 `id` 这一列。不加前缀，数据库不知道你要哪个。
别名让每一列的归属一目了然，也让 SQL 短很多。

**`LIMIT` 不能省。** 一篇爆款文章可能有几万条评论，
一次全查出来会让数据库、网络和浏览器同时卡住。
**任何"查列表"的接口都应该有上限**，这是一条通用纪律。

### 已写好 · 给每个人的评论数封一个顶

**为什么做这个**
不封顶的话，一个人写几行脚本就能灌进几十万条评论，
数据库和页面都会被拖垮。这类防护叫**限流**。

**涉及的知识点**

```js
const count = await db.query('SELECT COUNT(*) AS total FROM comments WHERE user_id=$1',
                             [req.user.sub])
if (Number(count[0].total) >= 200) return fail(res, 429, '评论数量已达体验上限')
```

|部分|说明|
|---|---|
|`COUNT(*)`|数一数有多少行|
|`AS total`|给结果起个名字，方便取|
|`429`|**Too Many Requests**——请求太多了|

**`429` 和 `400` 的区别很重要**：
这一条请求本身完全合法，只是**次数太多**。
用对状态码，前端才知道该提示"慢点"而不是"你填错了"。

这三样都在 `.gitignore` 里，正常不会出现；出现了说明 `.gitignore` 出了问题。

### 第三步：提交并推送

```bat
git add .
git commit -m "P2第09课：评论表外键、JOIN 查询、级联删除与限流"
git push origin main
```

**推送报 `'origin' does not appear to be a git repository` 怎么办？**
路线 B 克隆下来之后，`origin` 已经被改名成 `template`
（那是全班共用的模板仓库，**不能推**）。
先到 GitHub 新建一个空仓库 `p2-blog-09-学号`（**不要**勾选 "Add a README file"），然后：

**Windows CMD**

```bat
git remote add origin https://github.com/你的用户名/p2-blog-09-学号.git
git branch -M main
git push -u origin main
git remote -v
```

**Windows PowerShell**

```powershell
git remote add origin https://github.com/你的用户名/p2-blog-09-学号.git
git branch -M main
git push -u origin main
git remote -v
```

关联一次就够，以后 `git push origin main` 直接能用。
`git remote -v` 应该看到：`origin` 指向你自己的仓库，`template` 指向公共模板仓库。

## 常见问题

### 数据库

|现象|原因|处理|
|---|---|---|
|**改了建表语句没生效**|`CREATE TABLE IF NOT EXISTS` 不改已有的表|删掉 `var/blog.sqlite` 重启后端|
|**外键完全不起作用**|没写 `PRAGMA foreign_keys=ON`|这是本课最大的坑，见 已写好的代码|
|删文章时评论没跟着删|同上，或者建表时漏了 `ON DELETE CASCADE`|两处都要检查|
|发评论报 `FOREIGN KEY constraint failed`|`article_id` 或 `user_id` 指向了不存在的行|说明外键在正常工作；检查传的值对不对|
|删库后账号都没了|正常现象|重新注册；管理员靠 `.env` 里的配置重建|

### 接口

|现象|原因|处理|
|---|---|---|
|评论区显示数字不是昵称|已写好的代码 的 JOIN 没写|检查 SELECT 里有没有 `u.display_name`|
|报 `ambiguous column name: id`|两张表都有 id，没加表别名前缀|所有列都写成 `c.xxx` 或 `u.xxx`|
|发评论没反应|TODO 04 还在返回假的 id 0|补全 INSERT|
|发评论返回 401|没登录，或令牌过期|重新登录|
|发评论返回 404|文章不是已发布状态|检查 TODO 02；把文章状态改成已发布|
|用 curl 发评论返回 500|TODO 03 的类型判断没写|先判断 `typeof === 'string'` 再 `.trim()`|

### 提交

|现象|原因|处理|
|---|---|---|
|`git push` 报 `'origin' does not appear...`|来源已改名成 template|见第 6 节第三步|
|`var/` 出现在 `git status` 里|`.gitignore` 出了问题|**数据库文件绝不能提交**|
