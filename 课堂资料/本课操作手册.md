### 401 和 403 的区别（本课考点）

|状态码|意思|典型场景|前端该怎么办|
|---|---|---|---|
|`401`|**我不知道你是谁**|没登录、令牌无效、令牌过期|跳登录页|
|`403`|**我知道你是谁，但你不能干这个**|普通用户想删别人的评论|提示"没有权限"，**跳登录页毫无意义**|

**用错了前端就会做错事。** 一个登录了的用户收到 401 被踢去重新登录，
登完回来还是不能做那件事——因为问题从来不是"没登录"。

### 一个最小例子：中间件怎么把门

```js
function signed(req, res, next) {
  if (!req.user) return fail(res, 401, '请先登录')
  next()                    // 放行，交给下一环
}

app.post('/api/articles/:id/comments', signed, handler)
//                                      ↑ 先过这道门，过了才到 handler
```

`next()` 是"放行"。不调用它，请求就停在这里——
所以**每个分支要么 return 一个响应，要么调 `next()`**，两者必居其一。

### 这一课要建立的核心观念

> **前端藏起来是体验，后端挡住才是安全。**

把删除按钮藏掉，用户不会误点——这是好体验。
但按钮藏了，接口还在，任何人用一行 `curl` 就能调。
**真正的防线永远在服务器上。**

本课五个任务里，TODO 05 做的是前端拦截，其余六个都在后端。
这个比例本身就说明了问题。

### TODO 01 · `signed`：先问"登录了吗"

**难度**：极简单


**为什么做这个**
现在这个中间件直接放行，等于**所有需要登录的接口都没有保护**。
没登录的人可以发评论、删评论。

**涉及的知识点**

```js
function signed(req, res, next) {
  if (!req.user) return fail(res, 401, '请先登录')
  next()
}
```

`req.user` 是第 07 课 TODO 05 那个全局中间件放进去的：
令牌有效就是载荷对象，无效或没带就是 `null`。

**这里只问一个问题：登录了没有。** 至于"是不是管理员""是不是本人"，
那是 TODO 02 和 TODO 03 的事。**一个中间件只管一件事**，
这样才能自由组合：有的接口只要 `signed`，有的还要再加 `admin`。

**改哪里**：`server/blog-app.js` 顶部，TODO 01 的位置。

**操作前 / 操作后**

- 操作前：退出登录后还能发评论。
- 操作后：提示「请先登录」，状态码 401。

**自己验证**
1. 退出登录，在文章页试着发评论 → 提示「请先登录」。
2. **用 curl 不带令牌发一条**：

```bat
curl -X POST http://127.0.0.1:3000/api/articles/1/comments ^
  -H "Content-Type: application/json" ^
  -d "{\"body\":\"没登录也能发吗\"}"
```

应该返回 `401`。**返回 201 说明门没关上。**

**多想一步**
`signed` 保护的接口有哪些？在代码里搜一下 `signed` 就知道了：
发评论、删评论。**保护了几个接口，一眼能数清**——
这就是把权限判断集中成中间件的好处。

### TODO 02 · `admin`：再问"是不是管理员"

**难度**：简单


**为什么做这个**
登录了不等于什么都能干。普通用户不该能删文章、改文章。

**涉及的知识点**

```js
function admin(req, res, next) {
  if (!req.user) return fail(res, 401, '请先登录')
  if (req.user.role !== 'admin') return fail(res, 403, '仅管理员可管理文章')
  next()
}
```

**两个判断，两种状态码，顺序不能反：**

|情况|状态码|为什么|
|---|---|---|
|没登录|`401`|我不知道你是谁——你该去登录|
|登录了但不是管理员|`403`|我知道你是谁，你就是不能干这个——**去登录也没用**|

**角色从哪来？** `req.user.role` 来自令牌。令牌是服务器签的，用户改不了。
第 07 课那个"改坏令牌就变游客"的实验，验的就是这件事。

**为什么普通注册的用户一定是 `reader`？**
第 07 课 TODO 01 在建表时写了 `DEFAULT 'reader'`，
注册接口的 INSERT 里根本没有 `role` 这一列，所以只能是默认值。
**想成为管理员，只有首次建库时用环境变量创建这一条路。**
这是"约束 + 代码"配合的一个完整例子。

**改哪里**：`server/blog-app.js` 顶部，TODO 02 的位置（和 TODO 01 在一起）。

**操作前 / 操作后**

- 操作前：普通账号也能调删文章的接口。
- 操作后：返回 403「仅管理员可管理文章」。

**自己验证**
1. 用**普通账号**登录，拿到它的令牌（F12 → Application → Local Storage）。
2. 用这个令牌调删文章接口：

```bat
curl -X DELETE http://127.0.0.1:3000/api/articles/1 ^
  -H "Authorization: Bearer 普通账号的令牌"
```

应该返回 **403**。

3. **不带令牌**再调一次 → 应该返回 **401**。
4. **这两个状态码必须不一样。** 都返回 401 或都返回 403，说明判断写漏了一个。

**多想一步**
这个项目只有两种角色。真实系统常常有更细的权限，
比如"编辑只能改自己的文章""审核员只能改状态不能改正文"。
那时候就不够用一个 `role` 字段了，要引入"权限点"的概念：
每个角色拥有一组权限，中间件检查的是"有没有这个权限"而不是"是不是这个角色"。

**但思路完全一样**：把判断集中到一处，接口只负责声明"我需要什么权限"。

### TODO 03 · 只能删自己的评论

**难度**：简单


**为什么做这个**
**这是本课最能体现"授权"的一步。**

`signed` 和 `admin` 判断的是"你是什么身份"。
但这里要判断的是"**这个东西是不是你的**"——同样是登录用户，
张三能删张三的评论，不能删李四的。这叫**基于归属的授权**。

**涉及的知识点**

```js
if (!c) return fail(res, 404, '评论不存在')
if (Number(c.user_id) !== Number(req.user.sub) && req.user.role !== 'admin')
  return fail(res, 403, '只能删除自己的评论')
```

**`Number(...)` 这层转换绝对不能省。**

令牌里的 `sub` 和数据库里的 `user_id`，一个可能是字符串 `"3"`，一个是数字 `3`。
`"3" !== 3` 永远成立——结果就是**所有人都删不了自己的评论**。

这个 bug 特别隐蔽：功能"看起来在工作"（确实挡住了别人），
只是顺便把本人也挡住了。**凡是要比较两个来源的值，先统一类型。**

**管理员为什么能删所有人的？** 内容治理需要——
有人发了违规内容，管理员要能处理。这是产品决定，不是技术决定。

**改哪里**：`server/blog-app.js` 的 `DELETE /api/comments/:id`，TODO 03 的位置。

**操作前 / 操作后**

- 操作前：任何登录用户都能删掉别人的评论，只要猜一个编号。
- 操作后：**普通账号登录，别人评论上的删除按钮不会出现**；
  就算用 curl 直接调接口，也会被 403 挡住。

**自己验证（这一步要用两个账号）**
1. 用**管理员**在某篇文章下发一条评论。
2. 用**普通账号**（无痕窗口）打开同一篇文章：
   - 自己的评论**有**删除按钮；
   - 管理员那条评论**没有**删除按钮。
3. **重点：用 curl 绕过前端试一次。** 用普通账号的令牌去删管理员那条评论：

```bat
curl -X DELETE http://127.0.0.1:3000/api/comments/管理员那条的编号 ^
  -H "Authorization: Bearer 普通账号的令牌"
```

应该返回 **403**。**返回 204 说明前端藏了按钮但后端没挡住**——
这正是本课要讲的那件事。

4. 换管理员的令牌再调一次 → 应该成功（204）。

**多想一步**
第 3 步那个实验是本课的核心。
**前端藏按钮**和**后端挡请求**是两件完全不同的事：

- 只藏按钮：正常用户点不到，但懂一点技术的人一行命令就绕过去了。
- 只挡请求：安全没问题，但用户会看到一个点了就报错的按钮，体验很差。

**两个都要做。** TODO 05 做的就是前端那一半。

### TODO 04 · 编号只能是正整数

**难度**：简单


**为什么做这个**
地址栏里的编号是用户可以随便改的。
填 `abc`、填 `-1`、填一个 20 位的数字，后端会怎样？

不校验的话，`Number('abc')` 得到 `NaN`，拿去查数据库可能抛异常——
**用户乱填导致 500，这是我们的 bug，不是用户的错。**

**涉及的知识点：`app.param`**

```js
app.param('id', (req, res, next, value) => {
  if (!/^[1-9][0-9]*$/.test(value) || !Number.isSafeInteger(Number(value)))
    return fail(res, 400, '编号格式不正确')
  next()
})
```

`app.param` 是 Express 的一个便利功能：
**凡是路径里带 `:id` 的接口，都会先经过这里**，不用在每个接口里各写一遍。

本项目有六七个接口带 `:id`，写一处全覆盖。

|判断|挡住什么|
|---|---|
|`/^[1-9][0-9]*$/`|非数字、负数、`0`、以 0 开头的数字|
|`Number.isSafeInteger(...)`|大到超出安全范围的数字|

**为什么要查"安全整数"？** JavaScript 的数字超过 2^53 就会丢精度：

```js
9007199254740993 === 9007199254740992   // true —— 两个不同的数字变成相等了
```

传一个超长数字进来，`Number(...)` 得到的值和你以为的不是一回事。

**改哪里**：`server/blog-app.js` 的 `app.param('id', ...)`，TODO 04 的位置。

**操作前 / 操作后**

- 操作前：地址栏编号填 `abc`，后端抛异常返回 500。
- 操作后：返回 400「编号格式不正确」。

**自己验证**
1. 浏览器访问 `http://localhost:5173/articles/abc` → 提示编号格式不正确。
2. 用 curl 逐个试：

```bat
curl http://127.0.0.1:3000/api/articles/abc
curl http://127.0.0.1:3000/api/articles/-1
curl http://127.0.0.1:3000/api/articles/0
curl http://127.0.0.1:3000/api/articles/007
curl http://127.0.0.1:3000/api/articles/99999999999999999999
```

**五个都应该返回 400**，一个 500 都不能有。

3. 正常编号仍然能查：`curl http://127.0.0.1:3000/api/articles/1`。

**多想一步**
"在统一入口把好关"这个思路能省掉大量重复代码。
本项目还有两处同样的例子：
- 第 07 课 TODO 05 的全局中间件——所有接口统一解析令牌；
- 已写好的代码 的安全响应头——所有响应统一加上。

**凡是"每个接口都要做一遍"的事，都该往上提。**

### TODO 05 · 前端也要挡一道（体验层）

**难度**：中等


**为什么做这个**
前六个任务都在后端。**后端是安全，前端是体验。**

想象一个普通用户手滑点进了 `/admin/articles`：
后端每个接口都会返回 403，页面上就是满屏的错误提示——
**能用，但很难看**。前端提前拦住，直接弹回首页，体验好得多。

**涉及的知识点：路由守卫**

```js
router.beforeEach(to => {
  if (!to.meta.requiresAuth) return true                 // 不需要登录的页面，放行
  if (!getAccessToken())
    return { name: 'login', query: { redirect: to.fullPath } }   // 没令牌 → 去登录
  return readAuthSession()?.user?.role === 'admin'
    ? true                                               // 是管理员 → 放行
    : { name: 'home' }                                  // 不是 → 回首页
})
```

`beforeEach` 是"每次跳转之前都先问一下"。
返回 `true` 放行，返回一个路由对象就是"改去那里"。

**`query: { redirect: to.fullPath }` 这一段是个贴心设计**：
把用户原本想去的地址记下来，登录成功后自动跳回去。
没有它，用户登完发现自己在首页，还得再点一遍。

**改哪里**：`src/router.js`，TODO 05 的位置。

**操作前 / 操作后**

- 操作前：普通账号在地址栏输 `/admin/articles`，进到一个满屏 403 的空页面。
- 操作后：**直接被弹回首页**。

**自己验证**
1. 用**普通账号**登录，地址栏输入 `http://localhost:5173/admin/articles` → 回到首页。
2. **退出登录**再试一次 → 跳到登录页，**网址里带着 `?redirect=/admin/articles`**。
3. 在登录页用**管理员**登录 → **自动跳回 `/admin/articles`**。
4. **最重要的一步**：用普通账号的令牌直接调后端管理接口（绕过前端）：

```bat
curl -X DELETE http://127.0.0.1:3000/api/articles/1 ^
  -H "Authorization: Bearer 普通账号的令牌"
```

**仍然是 403。** 这证明前端这一道拦掉的只是"路"，真正的门在后端。

**多想一步**
把这句话记住：

> **前端代码全在用户的浏览器里，改一改就绕过去了。
> 任何"只在前端做的检查"，都等于没做。**

那前端这道还有什么用？**让正常用户不会莫名其妙撞进一个满屏报错的页面。**

这也是为什么本课五个任务里，**六个在后端、一个在前端**——
这个比例本身就是答案。

### 已写好 · 挡住暴力破解

**为什么做这个**
密码存成摘要（第 07 课）解决的是"**数据库被偷之后**"的问题。
但还有另一种攻击完全不需要偷数据库：**在线撞库**——
写个脚本对着登录接口一秒试几百个密码。

**涉及的知识点：滑动窗口限流**

```js
if (!a || now - a.time > 600000) a = { time: now, count: 0 }   // 超过 10 分钟重新计数
a.count++
attempts.set(key, a)
if (a.count > 40) return fail(res, 429, '操作过于频繁，请稍后重试')
```

|部分|说明|
|---|---|
|`key = req.ip`|按来源 IP 计数|
|`600000`|10 分钟（毫秒）。超过就重新开始数|
|`40`|10 分钟内最多 40 次|
|`429`|Too Many Requests|

它挂在 `app.use('/api/auth', ...)` 上，**注册和登录都受它保护**。

**这个实现有明确的边界，要讲清楚：**

|局限|后果|
|---|---|
|存在内存的 `Map` 里|**后端一重启就清空**|
|按 IP 计数|同一个学校/公司出口 IP 相同，会互相影响|
|多台服务器各记各的|部署两台，攻击者的次数就被分摊了|

**够课堂用，但不是生产级方案。** 真实项目会用 Redis 之类的共享存储，
并且按"IP + 账号"双维度计数。

**知道一个方案的边界在哪，比只会用它更重要。**

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 给每个响应加上安全头

**为什么做这个**
这是两行代码就能消除两类风险的事，几乎没有理由不做。

**涉及的知识点**

```js
res.set('Cache-Control', 'no-store')
res.set('X-Content-Type-Options', 'nosniff')
```

|响应头|防什么|
|---|---|
|`Cache-Control: no-store`|这些接口返回的是**和当前登录用户有关**的数据。被浏览器或中间的代理缓存下来，**换个人登录可能看到上一个人的数据**|
|`X-Content-Type-Options: nosniff`|禁止浏览器"猜"内容类型。不加的话，一个内容像 HTML 的文件可能被当成 HTML 执行|

第二个的实际场景：用户上传了一个叫 `a.txt` 但内容是 `<script>...</script>` 的文件，
浏览器"聪明地"认为这是 HTML 并执行了它——脚本就在你的域名下跑起来了。
`nosniff` 的意思是"**我说是什么就是什么，别猜**"。

**这两行写在全局中间件里，一次生效于所有接口。**
安全措施**能放在统一入口就不要分散**——分散了迟早漏掉一个。

## 常见问题

### 权限

|现象|原因|处理|
|---|---|---|
|所有接口都返回 401|`signed`/`admin` 里漏了 `next()`|每个分支要么 return 响应，要么调 next()|
|管理员也被 403 挡住|`.env` 里的管理员没建成功|`db:inspect` 看 users 表里有没有 role='admin' 的行|
|**自己的评论也删不掉**|忘了 `Number(...)` 转换|`"3" !== 3` 永远成立，两边要统一类型|
|普通账号能删别人评论|TODO 03 的条件写反了|应该是"不是自己的 **且** 不是管理员"才拒绝|
|401 和 403 返回成了同一个|`admin` 里少写了一个判断|两个 if 都要有，顺序是先 401 后 403|

### 限流与校验

|现象|原因|处理|
|---|---|---|
|429 一直不出现|上限没改小，或后端没重启|临时改成 3，看终端有没有打印重启|
|429 出现后一直不消失|窗口是 10 分钟|重启后端立刻清空（它存在内存里）|
|非法编号返回 500|TODO 04 没做|`app.param` 里补上校验|
|正常编号也被 400 挡住|正则写错了|`/^[1-9][0-9]*$/`，注意 `0` 是不允许的|

### 前端

|现象|原因|处理|
|---|---|---|
|路由守卫不生效|`to.meta.requiresAuth` 没配|看 `src/router.js` 里那条路由的 meta|
|登录后没跳回原页面|`query.redirect` 没传，或登录页没读它|两处都要检查|
|普通账号进了后台但全是报错|TODO 05 没做|前端守卫只是体验，后端已经挡住了，但要补上|

更多通用排错见 `通用附录_运行提交部署与排错.md`；
命令和参数的逐条解释见 [命令参数逐个拆开](<../../01_入门与通用规范/04_命令参数逐个拆开.md>)。
