## 本课在项目 3 里的位置

前两课的数据库都是**一个文件**：第 12 课是 `db.json`，第 13 课是 `.sqlite`。
它们的共同点是——**不需要账号密码，打开文件就能读**。

这一课换成 MySQL，它是一个**独立运行的服务**。于是第一次出现了三件新事：

1. **要用账号密码连过去**——第一次有了"不能写进代码里的东西"；
2. **数据库和应用可以不在同一台机器上**——这是生产部署的常态；
3. **前两课攒下的明文密码，必须在这次迁移中一起修好**。

|课次|工程|数据存在哪|这一课新出现的问题|
|---|---|---|---|
|12|`PersonaLink_NoDB`|一个 `db.json` 文本文件|并发写会互相覆盖；没有任何约束|
|13|`PersonaLink_SQLite`|一个 `.sqlite` 文件（Node 24 内置）|约束、外键、事务交给数据库|
|14|`PersonaLink_MySQL`|独立运行的 MySQL 服务|第一次有账号密码；密码不能明存|
|15|`PersonaLink_Docker`|PostgreSQL 容器 + 数据卷|环境怎么一键复制；数据怎么不跟着容器消失|

**四课做的是同一个产品**——界面、接口、功能完全一样，
差别只在**数据存在哪、怎么存**。所以这四课最值得记住的不是某一种数据库的语法，
而是：**换一种存储，同一件事该怎么做、代价是什么。**


**第三件事是这一课最有分量的部分。** 第 12、13 课的密码是明文存的，
你已经亲眼看过 `db.json` 里那一列。这一课迁移时逐条重新加密，
**用户完全无感，但数据库里从此没有明文了**。

### 前三课的密码，是怎么一步步变安全的

|课次|密码怎么存|被拖库的后果|
|---|---|---|
|12|`db.json` 里明文|**所有人的密码直接泄露**|
|13|`.sqlite` 里明文|同上，只是文件变成二进制的，用工具一样能看|
|**14（本课）**|**bcrypt 摘要**|拿到摘要也还原不出原密码，只能一个个暴力试|

**注意第 13 课并没有解决这个问题。** 换数据库和密码安全是两件独立的事——
很多人以为"用上数据库就安全了"，这是个很常见的误解。

### 一个最小例子：摘要为什么不可逆

```js
// 加密：同一个密码，每次结果都不同（因为盐不同）
await bcrypt.hash('123456', 12)
// → '$2b$12$K7L1OJ0/9NkDPIq...'
await bcrypt.hash('123456', 12)
// → '$2b$12$9xQm2Ff8Zt3rYuW...'   完全不一样

// 校验：不是"解密回来比一比"，而是"再算一次比对"
await bcrypt.compare('123456', 存在库里的那一串)   // true
await bcrypt.compare('wrong',  存在库里的那一串)   // false
```

**所以千万不要自己写 `hash(输入) === 库里的值` 来比**——
每次加密盐都不同，两个结果永远不相等。**只能用 `compare`。**

### 这一课要建立的核心观念

> **迁移不只是"把数据搬过去"，还是"把历史包袱修好"的机会。**

老系统总有历史问题：明文密码、不一致的格式、孤儿数据。
直接原样搬过去，等于把问题也搬了过去，而且以后更难改
（数据量更大、用的人更多）。

**迁移的那一刻，是修历史包袱成本最低的时候。**

### TODO 01 · 连接信息必须从 `.env` 读

**难度**：极简单


**为什么做这个**
第 13 课的 SQLite 是一个本地文件，不需要账号密码。
MySQL 是独立服务，要用账号密码连过去——
**于是第一次出现了"不能写进代码里的东西"。**

**涉及的知识点**

```js
const pool = mysql.createPool({
  host: process.env.DB_HOST || '127.0.0.1',
  port: Number(process.env.DB_PORT || 3306),
  user: process.env.DB_USER || 'personalink',
  password: process.env.DB_PASSWORD || '',
  database: process.env.DB_NAME || 'personalink',
  connectionLimit: Number(process.env.DB_CONNECTION_LIMIT || 10),
})
```

|概念|说明|
|---|---|
|`process.env.XXX`|读环境变量。`.env` 文件里的值会被 `dotenv` 加载进来|
|`\|\| '默认值'`|环境变量没设时用默认值，方便本机开发|
|**连接池**|预先建好若干条连接反复用。每次查询都重新连的话，光握手就要几十毫秒|
|`connectionLimit`|池子里最多几条连接。太小会排队，太大会把数据库拖垮|

**为什么绝对不能把密码写在源码里？**

源码要进 Git、要分享给同学、要发到服务器上。
**密码一旦进了 Git 历史，删掉也没用**——历史里还在，
任何克隆过仓库的人都有。只能去改密码。

**改哪里**：`backend/db.js`，TODO 01 的位置。

**操作前 / 操作后**

- 操作前：连接信息写死成 `root` / `123456`，换台机器就连不上。
- 操作后：从 `.env` 读，代码里一个真实密码都没有。

**自己验证**
1. `npm run db:verify` → 能连上并打印表结构。
2. **故意把 `.env` 里的密码改错一个字符，再跑一次** →
   报 `Access denied`。改回去。
   这一步证明它**真的在读 `.env`**，而不是用代码里的默认值。
3. **确认 `.env` 没被 Git 跟踪**：

```bat

```

第二条应该打印出是哪条规则忽略了它。

**多想一步**
`|| '默认值'` 这个写法有利有弊：

- 好处：本机开发不用配 `.env` 也能跑起来。
- 坏处：**生产环境忘了配，它会静悄悄用默认值连上一个错的库**。

### TODO 02 · MySQL 的约束写法

**难度**：简单


**为什么做这个**
第 13 课在 SQLite 里写过一遍约束。这一课换成 MySQL，
**概念完全一样，但写法有几处不同**——正好对照着记。

**涉及的知识点**

|  |SQLite|MySQL|
|---|---|---|
|字符串列|`email TEXT`|`email VARCHAR(255)`——**必须指定长度**|
|自增主键|`INTEGER PRIMARY KEY`|`INT AUTO_INCREMENT PRIMARY KEY`|
|约束命名|通常不命名|`CONSTRAINT uq_users_email UNIQUE (email)`|

**MySQL 为什么要求指定长度？** 因为它要为索引预分配空间，必须知道最大长度。
SQLite 的类型系统很松散，`TEXT` 可以存任意长度。

**为什么要给约束起名字？** 违反约束时，MySQL 的报错信息里会带上这个名字：

```text
Duplicate entry 'a@x.com' for key 'uq_users_email'
```

**一眼就知道是哪条约束被违反了**，不用去猜。表大了、约束多了，这很省事。

**改哪里**：`backend/database/schema.sql`，TODO 02 的位置。

**操作前 / 操作后**

- 操作前：email 列没有约束，同邮箱能写两次。
- 操作后：第二次被数据库挡住。

**自己验证**
**改了建表脚本要重新执行**：

```bat
npm run db:schema
npm run db:verify
```

然后页面上用同一个邮箱注册两次 → 第二次被拒。

**多想一步**
这一课要对照着记的"方言差异"不止这一条。
关系型数据库的**核心概念是通用的**（表、列、约束、外键、事务、索引），
真正要重新学的只有语法细节。

**所以学数据库要学概念，不要背某一种的语法。**
换一种数据库时，你要查的是"这个概念在这里怎么写"，而不是从头学一遍。

### TODO 03 · 迁移之后必须逐项核对

**难度**：中等


**为什么做这个**
> **数据迁移最危险的不是失败，是"看起来成功了"。**

少搬了 3 条、某个字段错位了、外键指向了不存在的班级——
这些都**不会报错**，等用户投诉时才发现，那时候源数据可能已经删了。

**涉及的知识点**

```sql
SELECT COUNT(*) AS total FROM users u
LEFT JOIN classes c ON c.id = u.class_id
WHERE u.class_id IS NOT NULL AND c.id IS NULL
```

这条 SQL 在找**孤儿用户**：有班级 id，但那个班级不存在。

|部分|作用|
|---|---|
|`LEFT JOIN`|左表全保留，右表没配上的填 NULL|
|`c.id IS NULL`|**右表没配上** → 说明这个 class_id 在 classes 里找不到|

**`LEFT JOIN + IS NULL` 是找孤儿数据的标准写法**，值得记住。

**改哪里**：`backend/scripts/verify-mysql.js`，TODO 03 的位置。

**操作前 / 操作后**

- 操作前：报告里孤儿数恒为 0（写死的），等于没查。
- 操作后：真的查一遍，有问题能报出来。

**自己验证**
1. `npm run db:verify` → 报告里 `orphanUsers` 有真实数字（正常应该是 0）。
2. **故意造一个孤儿**：

```bat
mysql -u personalink -p -e "UPDATE personalink.users SET class_id='不存在的班级' WHERE id=(SELECT id FROM (SELECT id FROM personalink.users LIMIT 1) t);"
```

再跑 `db:verify` → **`orphanUsers` 应该变成 1**。

3. 改回去（重新跑一次迁移最简单）。

**多想一步：迁移三件套**

```text

② 搬之后数一遍（db:verify）
③ 两个数对得上
```

**这一条纪律能挡掉绝大多数迁移事故。**

而且核对项不该只有"条数"。这个项目核对的是：
用户数、班级数、孤儿数、管理员存不存在、密码是否全部已加密。
**每一项都对应一种真实会出问题的情况。**

### TODO 04 · MySQL 怎么备份

**难度**：中等


**为什么做这个**
前两课的备份就是复制一个文件。MySQL 不行——
数据分散在很多文件里，而且数据库还在写，**直接复制目录拿到的是一个坏掉的快照**。

**涉及的知识点**

```powershell
mysqldump --single-transaction --quick --routines --triggers ^
  --default-character-set=utf8mb4 --result-file=$temporaryFile $DbName
```

|参数|作用|
|---|---|
|`--single-transaction`|**在一个事务里导出**，导出期间数据库照常读写，拿到的是一致快照，**不用停服务**|
|`--quick`|逐行取而不是一次全读进内存，大表才不会撑爆|
|`--routines --triggers`|把存储过程和触发器也备份上|
|`--result-file=`|直接写文件，比用 `>` 重定向更可靠（不会有编码问题）|
|`--default-character-set=utf8mb4`|**中文和 emoji 才不会变成问号**|

`mysqldump` 导出的是一份 **SQL 文本**，里面是一条条 `CREATE TABLE` 和 `INSERT`。
用记事本就能打开看——这是它相比二进制备份的一大好处。

**改哪里**：`scripts/backup-mysql.ps1`，TODO 04 的位置。

**操作前 / 操作后**

- 操作前：备份命令不完整，导不出东西。
- 操作后：生成一个 `.sql` 文件，打开能看到熟悉的 SQL 语句。

**自己验证**
1. 跑备份，生成 `.sql` 文件。
2. **用记事本打开看一眼**——里面是 `CREATE TABLE` 和 `INSERT INTO`。
3. **演练一次恢复**（必做）：

```text

→ npm run db:verify → 数字和删之前对得上
```

**多想一步：三课的备份方式对照**

|课次|存储|备份方式|注意什么|
|---|---|---|---|
|12|JSON 文件|复制一个 `.json`|写入过程中复制会拿到半截文件|

### 已写好 · 把明文密码换成 bcrypt 摘要

**为什么做这个**
**这是整个项目 3 最重要的一个安全改进。**

第 12、13 课的密码是明文存的——你已经亲眼看过 `db.json` 里那一列。
这一课彻底解决它。

**涉及的知识点**

```js
const hashPassword = (password) => bcrypt.hash(String(password), 12)
```

|部分|说明|
|---|---|
|`bcrypt.hash`|把密码算成一串不可逆的摘要|
|`12`|**代价因子**。每加 1，计算量翻一倍。12 大约 0.2—0.3 秒|
|`String(...)`|万一传进来一个数字，bcrypt 会报类型错误|

**为什么要"慢"？** 这是 bcrypt 最反直觉、也最关键的设计。

|  |用 SHA-256 直接算|用 bcrypt（代价 12）|
|---|---|---|
|正常登录|几微秒|0.2 秒（用户完全无感）|
|攻击者穷举|**一秒能试几十亿个**|一秒只能试几个|

**慢是故意的。** 千万不要用 md5 / sha1 / sha256 直接算密码——
它们快得正好帮了攻击者。

**盐是怎么回事？** bcrypt 每次加密都会生成一个随机盐拼进去，
所以**同一个密码两次加密结果完全不同**。
这样攻击者拿到数据库之后，不能一次破解一批人——只能一个个来。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 用 `bcrypt.compare` 校验

**为什么做这个**
摘要是**不可逆**的，所以校验不是"解密回来比一比"，
而是"把用户输入的密码用同样的方法再算一次，比对两个摘要"。

**涉及的知识点**

```js
return bcrypt.compare(plainPassword, storedPassword)
```

**为什么不能自己写 `hash(输入) === 库里的值`？**

因为 bcrypt 每次加密都用新的随机盐，同一个密码两次加密结果**完全不同**。
自己算一遍去比，**永远不相等**——所有人都登不进去。

`compare` 会**从 `storedPassword` 里把盐读出来**，用同一个盐重新算，再比对。
这是唯一正确的做法。

`compare` 内部还用了**恒定时间比较**：不管密码对不对都花一样的时间。
否则攻击者能靠响应快慢一个字节一个字节地试出摘要（**时序攻击**）。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 迁移时把旧的明文密码转成摘要

**为什么做这个**
**这是本课最有价值的一步，也是真实项目里经常要做的事。**

第 12 课的 `db.json` 里有 28 条明文密码。
直接搬到 MySQL，等于把问题原样带过去。
正确做法是：**迁移时逐条重新加密**。

**涉及的知识点**

```js
return hashPassword(user.password || '123456')
```

对每个用户，不是原样搬 `user.password`，而是把它**当作明文重新加密一遍**。

**关键问题：这样做之后，用户原来的密码还能用吗？**

**能。** 因为摘要是从同一个明文算出来的，登录时 `compare` 一样能通过。
**用户完全无感，但数据库里从此没有明文了。**

## 常见问题

### 连接

|现象|原因|处理|
|---|---|---|
|`ECONNREFUSED`|MySQL 服务没起来|Windows 服务里启动 MySQL；或检查端口|
|`Access denied for user`|账号或密码不对|检查 `.env`；**注意密码里的 `#` 会截断值**|
|`Unknown database 'personalink'`|库还没建|先 `npm run db:schema`|
|改了 `.env` 不生效|`.env` 只在启动时读一次|**重启后端**|
|连上了但查不到表|建表脚本没跑，或连错了库|`npm run db:schema`；确认 `DB_NAME`|

### 密码与迁移

|现象|原因|处理|
|---|---|---|
|所有人都登不进去|已写好的代码 没做，或自己写了 `===` 比对|必须用 `bcrypt.compare`|
|`not_hashed` 不是 0|已写好的代码 没做，原样搬了明文|迁移脚本里要 `hashPassword(...)`|
|迁移报外键错误|某个用户的 classId 在 classes 里不存在|先修数据，或检查迁移顺序（先班级后用户）|
|迁移后用户数对不上|源文件不对，或迁移中途失败|`db:inspect-json` 先确认源头|
|中文变成问号|字符集不是 utf8mb4|建库和连接都要指定 utf8mb4|

### 备份

|现象|原因|处理|
|---|---|---|
|`mysqldump was not found`|MySQL 客户端没装或不在 PATH|装 MySQL Client，把 bin 目录加进 PATH|
|导出的文件是空的|命令执行失败了|看 `$LASTEXITCODE`；脚本里有检查|
|恢复后中文乱码|导出时没指定字符集|加 `--default-character-set=utf8mb4`|

更多通用排错见 `通用附录_运行提交部署与排错.md`；
命令和参数的逐条解释见 [命令参数逐个拆开](<../../01_入门与通用规范/04_命令参数逐个拆开.md>)。
