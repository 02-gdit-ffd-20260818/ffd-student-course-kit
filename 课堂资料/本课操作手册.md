### 本课要用到的 HTTP 方法

|方法|意思|本课的接口|
|---|---|---|
|`GET`|取数据，**不改变任何东西**|`GET /api/articles`|
|`POST`|新建一个|`POST /api/articles`|
|`PUT`|整体替换一个|`PUT /api/articles/:id`|
|`DELETE`|删掉一个|`DELETE /api/articles/:id`|

**`GET` 不能有副作用**，这是一条铁律。
写成 `GET /api/articles/5/delete` 这种接口会出事——
浏览器预加载、搜索引擎爬虫、甚至聊天软件生成预览，都会自动发 `GET` 请求。
真出现过网站被爬虫"点"光所有删除链接的事故。

### 一个最小例子：同一段代码处理新增和修改

```js
for (const method of ['post', 'put'])
  app[method](method === 'post' ? '/api/articles' : '/api/articles/:id', admin, handler)
```

新增和修改的校验、字段处理**完全一样**，只有 SQL 和状态码不同。
与其写两份几乎一样的代码（改一处忘一处），不如合成一处、用 `method` 区分。

**这一课要建立的核心观念**：

> **权限判断必须放在后端，而且要"不该给的数据一开始就不查出来"。**

前端"把草稿藏起来不显示"是没用的——数据已经发到浏览器了，F12 一看全在。

### TODO 01 · 给文章表加上约束

**难度**：极简单


**为什么做这个**
和第 07 课的用户表一样：**表结构定错了，后面所有课都在错的地基上盖房子。**

**涉及的知识点**

|约束|作用|不写会怎样|
|---|---|---|
|`slug ... UNIQUE`|文章地址不能重复|两篇文章抢同一个网址，打开哪篇全看运气|
|`status ... CHECK(...)`|状态只能是 draft 或 published|拼错成 `publish`，这篇文章从此谁都看不到|
|`media_json ... DEFAULT '[]'`|不填时用空数组|值是 NULL，前端 `JSON.parse(null)` 直接报错|

**为什么正文用 JSON 文本存在一列里，而不是再建一张"段落表"？**
因为正文永远是**整篇一起读、整篇一起改**，从来不需要"查出第 3 段"。
建段落表反而要多一次 JOIN、多一次排序。
**按使用方式设计表结构**，不是拆得越细越对。

**改哪里**：`server/blog-db.js` 里 `articles` 表的建表语句，TODO 01 的位置。

**操作前 / 操作后**

- 操作前：两篇文章能用同一个链接名；状态可以写成任意字符串。
- 操作后：数据库自己挡住这两种情况。

### TODO 02 · 草稿不能给游客看见

**难度**：简单


**为什么做这个**
**这是本课最直观的一个效果**，也是整个项目第一次出现"按身份给不同数据"。

**涉及的知识点**

```js
req.user?.role === 'admin'
  ? 'SELECT * FROM articles ORDER BY id'
  : "SELECT * FROM articles WHERE status='published' ORDER BY id"
```

`req.user` 是第 07 课 TODO 05 那个全局中间件放进去的。
游客身份下它是 `null`，`?.` 可选链让这里不会报错，直接走后半段。

**关键在于：不该给的数据，一开始就不要查出来。**

对比两种做法：

|做法|问题|
|---|---|
|❌ 查出全部，前端判断"草稿不显示"|数据已经发到浏览器了，F12 → Network 一看全在|
|✅ 后端按身份查不同的数据|游客的响应里**根本没有草稿那几条**|

**改哪里**：`server/blog-app.js` 的 `GET /api/articles`，TODO 02 的位置。

**操作前 / 操作后**

- 操作前：不管登没登录，首页都能看到草稿。
- 操作后：管理员登录时首页有草稿；**退出登录再刷新，草稿消失**。

**自己验证**
1. 用管理员登录，在管理页把一篇文章的状态改成"草稿"（TODO 04 做完之后才能改，
   现在可以先用 `db:inspect` 确认库里有草稿，或者等做完 TODO 04 再回来验）。
2. 首页能看到它。
3. **退出登录，刷新**——它不见了。
4. **重点**：F12 → Network → `/api/articles` 的响应，
   游客身份下**整个响应里搜不到那篇草稿的标题**。

**多想一步**
这条思路有个名字叫"**最小权限**"：每个请求只拿到它该拿到的那部分数据。
它比"发全量数据再由前端过滤"安全得多，也快得多（传输量小）。
后面第 10 课的权限中间件是同一个思路的延伸。

### TODO 03 · 标题和摘要必须校验

**难度**：简单


**为什么做这个**
标题可以是空的，也可以是一万字——存进去之后列表页会被撑爆。
而且和第 07 课一样，**前端的表单校验挡不住 curl**。

**涉及的知识点：按字段收集错误**

```js
const errors = {}
if (!title) errors.title = 'title required'
if (!summary) errors.summary = 'summary required'
// ……全部查完，最后一起返回
return errors
```

**注意错误是收集到一个对象里，而不是遇到第一个就返回。**

|做法|用户体验|
|---|---|
|❌ 遇到第一个错就返回|改一个、保存、又报一个，来回折腾五次|
|✅ 全部收集一起返回|前端把每条错误标在对应输入框上，一次改完|

前端拿到的响应形如：

```json
{ "error": { "message": "请检查文章内容",
              "fields": { "title": "title required" } } }
```

`fields` 里的键就是输入框的名字，前端据此把红色提示标到正确的位置。

**改哪里**：`server/services/articleInput.js`，TODO 03 的位置。

**操作前 / 操作后**

- 操作前：标题清空点保存，也能保存成功（存进去一篇没标题的文章）。
- 操作后：**标题输入框下方出现红色提示**，保存被拒绝。

**自己验证**
1. 管理页新建文章，标题留空，点保存 → 标题框下出现提示。
2. 标题填一个超过 60 字的长句 → 同样被拒。
3. **把标题和摘要同时留空** → **两个框下面同时出现提示**。
   这一步专门验"按字段收集"——如果只有一个框有提示，说明写成了"遇错就返回"。
4. F12 → Network 看那条请求的响应，`fields` 里应该有两项。

**多想一步**
`validateArticleInput` 这个函数**不碰数据库、不碰 Express**，
输入一个对象、输出一个对象。这样的函数最好测——
`tests/backend.test.mjs` 里可以直接给它喂各种坏输入，不用起服务器。
**把"纯判断"的逻辑从"要联网要连库"的代码里拆出来**，是写可测试代码的第一步。

### TODO 04 · 把文章真的写进数据库

**难度**：中等


**为什么做这个**
**这是本课最有成就感的一步。** 前五个任务都在做约束和校验，
这一个才让"新建文章"真正能用。

**涉及的知识点**

```js
// 新增
'INSERT INTO articles(slug,title,...) VALUES($1,$2,...,$9) RETURNING *'
// 修改
'UPDATE articles SET slug=$1,title=$2,... WHERE id=$10 RETURNING *'
```

|要点|说明|
|---|---|
|`$1`—`$9`|与上面 `values` 数组**逐项对应**，顺序不能乱|
|`RETURNING *`|写完之后把那一行返回给我们，**省掉一次额外的 SELECT**|
|PUT 多一个 `$10`|就是 id。上面有一行 `if (method === 'put') values.push(...)`|

**为什么新增和修改写在一个处理函数里？**
它们的校验、字段处理**完全一样**，只有 SQL 和状态码不同。
写两份几乎一样的代码，改一处忘一处是迟早的事。

**绝对不要用字符串拼接 SQL。** 标题里写一段 SQL 就能操作你的数据库。

**改哪里**：`server/blog-app.js` 那个 `for (const method of ['post', 'put'])` 里面，
TODO 04 的位置。

**操作前 / 操作后**

- 操作前：管理页新建文章点保存，什么都不会发生（SQL 是占位的 `SELECT 1`）。
- 操作后：**列表里真的多出一篇**；改一篇的标题保存，列表里的标题跟着变；
  重启后端再看，它们还在。

**自己验证**
1. 管理页新建一篇文章（状态选"已发布"），保存 → 列表多一篇。
2. 回首页，能看到它。
3. 改一下标题保存 → 列表里的标题变了。
4. `npm run db:inspect` → `articles` 的条数增加了。
5. **终端 1 按 Ctrl+C 停掉后端再重启**，刷新页面 → 文章还在。
   **这一步是"存进数据库"和"只存在内存里"的分界线。**

**多想一步**
新增返回 `201`、修改返回 `200`，这个区别值得留意：

```js
res.status(method === 'post' ? 201 : 200).json(...)
```

201 表示"**创建**了一个新资源"，响应里通常还会带上它的位置。
200 就是"成功了"。用准确的状态码，前端不用解析响应内容就知道发生了什么。

### TODO 05 · 删掉不存在的东西要说清楚

**难度**：中等


**为什么做这个**
删除是四件事里**最危险**的一个——删错了通常拿不回来。
所以它要把"到底删没删掉"说清楚。

**涉及的知识点**

```js
const rows = await db.query('DELETE FROM articles WHERE id=$1 RETURNING id', [...])
if (!rows.length) return fail(res, 404, '文章不存在')
res.sendStatus(204)
```

`DELETE ... RETURNING id` 的巧妙之处：**真的删掉了才会返回一行，
什么都没删返回空数组**。靠它就能分辨"删成功"和"本来就没有"，
不用先 SELECT 一次再 DELETE。

**`204` 是什么？** "成功，但没有内容要返回"。
删除成功后没什么好给的，用 204 比返回 `200 {}` 更准确。

**改哪里**：`server/blog-app.js` 的 `DELETE /api/articles/:id`，TODO 05 的位置。

**操作前 / 操作后**

- 操作前：删一个不存在的编号，也返回"成功"。
- 操作后：删掉一篇，**列表里立刻少一篇**；删已经被删过的，提示「文章不存在」。

**自己验证**
1. 管理页删掉一篇文章 → 列表少一篇，首页也没了。
2. `npm run db:inspect` → `articles` 条数减少。
3. **用 curl 删一个不存在的编号**：

```bat
curl -X DELETE http://127.0.0.1:3001/api/articles/99999 ^
  -H "Authorization: Bearer 你的令牌"
```

应该返回 `404`。**返回 204 就说明没做对**——它在假装删成功了。

> 令牌从 F12 → Application → Local Storage 里复制。

**多想一步**
真实的内容系统很少**真删**，通常是"软删除"：加一列 `deleted_at`，
删除时只是写上时间，查询时统一过滤掉。
好处是误删能恢复、能审计"谁在什么时候删的"。
代价是所有查询都要记得加上过滤条件，漏一处就会把已删内容显示出来。
**没有免费的设计**，选哪种取决于"误删的代价"和"忘记过滤的风险"哪个更大。

### 已写好 · 链接名只许英文数字短横线

**为什么做这个**
slug 是文章网址里的那一段，比如 `/articles/html5-media` 里的 `html5-media`。
它会出现在网址、分享链接、搜索引擎结果里。

**涉及的知识点**

```js
/^[a-z0-9][a-z0-9-]{0,99}$/.test(input.slug.trim())
```

|部分|意思|
|---|---|
|`^[a-z0-9]`|必须以小写字母或数字开头（**不能以短横线开头**）|
|`[a-z0-9-]{0,99}`|后面最多 99 个小写字母、数字或短横线|
|`$`|到此为止，整体匹配|

**为什么不许中文？** 网址里的中文要做百分号编码：
`我的文章` 会变成 `%E6%88%91%E7%9A%84%E6%96%87%E7%AB%A0`——
又长又难读，复制粘贴还容易断。

**为什么不能以短横线开头？** 有些工具会把 `-` 开头的字符串当成命令行参数。
这类"看起来无所谓"的限制，往往是被坑过之后加上的。

## 常见问题

### 数据库

|现象|原因|处理|
|---|---|---|
|**改了建表语句没生效**|`CREATE TABLE IF NOT EXISTS` 不改已有的表|删掉 `var/blog.sqlite` 重启后端|
|删库后管理员没了|管理员只在首次建库时创建|`.env` 里填好 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 再重启|
|保存文章报 `SQLITE_CONSTRAINT`|违反了 UNIQUE 或 CHECK|换一个链接名；确认状态是 draft 或 published|
|`media_json` 报 NULL 错误|建表时漏了 `DEFAULT '[]'`|补上并删库重建|

### 接口

|现象|原因|处理|
|---|---|---|
|保存文章没反应|TODO 04 的 SQL 还是占位的 `SELECT 1`|补全 INSERT / UPDATE|
|保存返回 403|不是管理员账号|用 `.env` 里那个管理员登录|
|草稿退出后还能看到|TODO 02 没做，或前端缓存|`Ctrl+F5` 强刷；确认后端两条 SQL 都写了|
|详情返回 200 但内容为空|已写好的代码 的判断写反了|`!a ||` 后面那段是"不是已发布 **且** 不是管理员"|
|Network 里是 500|后端抛异常|**看终端 1 的输出**，那里有完整堆栈|
|删除返回 204 但列表没变|前端没刷新|正常现象，刷新页面看；或检查前端有没有重新拉列表|
