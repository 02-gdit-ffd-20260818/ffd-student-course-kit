### 这一课要建立的三条核心观念

> **① 用户传上来的东西，声明的和实际的可能不是一回事。**

把 `virus.exe` 改名成 `photo.png`，浏览器会老老实实声明它是 `image/png`。
**只查扩展名和 MIME 是不够的，要读文件开头的字节。**

> **② 同一份代码，在不同的部署环境下能力是不一样的。**

Netlify、Vercel 这类平台的服务器是**用完即弃**的，
你传上去的文件下一次请求可能就找不到了。
只有部署在自己的服务器上，才有可持久化的磁盘。

> **③ 没有验证过恢复流程的备份，等于没有备份。**

这句话在真实事故里被反复印证——
**很多团队是在需要恢复的那一刻，才发现备份脚本半年前就坏了。**

|终端|端口|负责什么|关掉会怎样|
|---|---|---|---|
|1（后端）|3001|接口、数据库、登录鉴权|页面能打开，但所有数据都加载不出来|
|2（前端）|5173|页面本身|浏览器直接打不开|

**前端怎么找到后端的？** 看 `vite.config.js` 里的 `server.proxy` 配置：
前端把 `/api` 开头的请求**转发**到 3001。
所以你在浏览器里看到的地址始终是 5173，但 `/api/...` 的请求实际上是后端在回应。
这样浏览器认为前后端同源，不会有跨域问题。

> **两个终端都要开着。** 只开前端，页面能打开但一片空白、Console 里全是请求失败；
> 只开后端，浏览器根本打不开页面。改后端代码时 `--watch` 会自动重启，
> 改前端代码 Vite 会自动刷新，都不用手动重启。


用管理员账号登录，进入任意一篇文章的编辑页——
**这一课的上传功能就在编辑页的媒体区**。

1. **终端里出现了上面说的那行提示**，而不是一串红色报错。
2. **浏览器真的能打开页面**，不是"无法访问此网站"。
3. **这些终端要一直开着。** 关掉哪个，哪一半功能就没了。

**改了代码要不要重启？**

|改什么|要不要手动重启|
|---|---|
|前端代码（页面、组件、样式）|**不用**，保存后浏览器自动刷新|
|后端代码|**不用**，`--watch` / `nodemon` 会自动重启|

|终端里报什么|原因|处理|
|---|---|---|
|`'npm' 不是内部或外部命令`|Node 没装，或装完没重开终端|装 Node 24，**关掉所有终端重开**，再 `node -v` 确认|

|`EADDRINUSE` 端口被占用|**多半是上一次的服务没关**|找到那个终端按 `Ctrl+C`；或者换个端口|
|`npm ci` 报 lock 文件对不上|`package.json` 改过但没更新 lock|先 `npm install` 生成新的 lock，再提交|
|装依赖卡住不动|npm 源慢|`npm config set registry https://registry.npmmirror.com` 再重试|
|页面能打开但数据是空的|**后端没起来**|F12 → Network，看那条请求是红的还是 200|
|一片空白，Console 全是红字|前端代码有错|从 **第一条**报错开始看，不要直接翻到最后|

### TODO 01 · 把媒体上传接口打开

**难度**：极简单


**为什么做这个**
现在这个条件永远为假，媒体上传相关的路由**一条都没注册**——
管理员在编辑页选了图片也传不上去，接口返回 404。

**涉及的知识点**

```js
if (db.driver === 'SQLite') {
  // 注册上传接口和静态文件服务
} else {
  // 返回 503，明确告诉前端"这个环境不支持"
}
```

**为什么要有这个条件？** 上传的文件要落到磁盘上。

|部署方式|有没有持久化磁盘|
|---|---|
|自己的 Ubuntu 服务器|**有**。文件写进 `/var/www/.../media`，重启还在|
|Netlify / Vercel 等平台|**没有**。服务器用完即弃，写进去的文件下次请求就找不到了|

所以同一份代码，在不同环境下能力不一样。
**要在代码里把这件事表达出来**，而不是装作没有区别——
后者的结果是用户传完图片，刷新发现图片裂了，还不知道为什么。

注意 `else` 分支返回的是 `503`（服务不可用）加一句人话，
而不是让请求悄悄失败。

**改哪里**：`server/blog-app.js`，TODO 01 的位置。

**操作前 / 操作后**

- 操作前：编辑页选图片点上传，接口 404。
- 操作后：**图片真的传上去，并显示在文章里**。

**自己验证**
1. 用管理员登录，进文章编辑页，选一张 PNG 或 JPG 上传 → 成功。
2. 保存文章，回到文章页 → **图片显示出来了**。
3. 看看文件落到哪了：

**Windows CMD**

```bat
dir var\media
```

**Windows PowerShell**

```powershell
Get-ChildItem var\media
```

能看到一个以 UUID 命名的文件。

4. F12 → Network，图片的请求路径是 `/media/uploads/xxx.png`，状态码 200。

**多想一步**
为什么文件名要改成随机 UUID，不用原来的名字？三个原因：

- **防重名**：两个人都传 `photo.png`，后一个会覆盖前一个；
- **防猜测**：用原名的话，别人能猜到 `/media/uploads/合同.pdf` 这种地址；
- **防路径穿越**：文件名里如果有 `../`，可能被写到目录之外。

**永远不要直接用用户提供的文件名当磁盘文件名。**

### TODO 02 · 只收白名单里的文件类型

**难度**：简单


**为什么做这个**
不限制类型的话，用户可以上传任何东西：可执行文件、HTML、脚本。

**涉及的知识点**

```js
const accept = new Set([
  'image/png', 'image/jpeg', 'image/webp',
  'audio/mpeg', 'audio/wav', 'audio/x-wav', 'audio/ogg',
  'video/mp4', 'video/webm',
])
```

**为什么用白名单不用黑名单？** 和第 07 课的场景校验一样：
危险的类型列不完（exe、bat、cmd、scr、js、html、svg……），漏一个就出事。
白名单只有九种，列得全。

**为什么 `.html` 和 `.svg` 一定要挡？**
它们能带 `<script>`。如果上传的文件和网站**同域名**，
别人打开这个文件时，脚本就在你的域下执行了——
能读到同域的 Cookie 和 localStorage，等于账号被接管。

**改哪里**：`server/media-upload.js` 里的 `accept` 集合，TODO 02 的位置。

**操作前 / 操作后**

- 操作前：`accept` 是空集合，什么都不收，上传永远失败。
- 操作后：正常的 jpg/png/mp3/mp4 能传；`.exe`、`.html` 被明确拒绝。

**自己验证**
1. 上传一张正常的 PNG → 成功。
2. **上传一个 `.txt` 文件** → 提示「只接受PNG/JPEG/WebP、MP3/WAV/OGG、MP4/WebM」。
3. 随便找一个 `.exe`（比如某个安装包）上传 → 同样被拒。
4. F12 → Network 看那条请求，状态码是 `400`。

**多想一步**
`limits: { fileSize: 40 * 1024 * 1024, files: 1, fields: 0 }` 这一行也很重要：

|限制|防什么|
|---|---|
|`fileSize` 40MB|防止有人传一个 10GB 的文件把磁盘塞满|
|`files: 1`|一次只能传一个|
|`fields: 0`|不接受额外的表单字段|

**限制永远要在"开始接收"之前设**，而不是收完再检查——
收完才发现太大，磁盘已经写满了。

### 已写好 · 光看声明的类型不算数

**为什么做这个**
**这是本课最重要的一个安全观念。**

TODO 02 检查的是浏览器**声明**的 MIME 类型。但声明是可以伪造的——
把 `virus.exe` 改名成 `photo.png`，浏览器会老老实实说它是 `image/png`。

**涉及的知识点：魔数（magic number）**

文件开头的几个字节是格式的"指纹"，**这个骗不了人**：

|格式|开头的字节|
|---|---|
|PNG|`89 50 4E 47 0D 0A 1A 0A`|
|JPEG|`FF D8 FF`|
|WebP|`RIFF` + 4 字节 + `WEBP`|
|WAV|`RIFF` + 4 字节 + `WAVE`|
|OGG|`OggS`|
|MP3|`ID3` 或 `FF Ex`|
|MP4|第 5—8 字节是 `ftyp`|
|WebM|`1A 45 DF A3`|

上面那一大段 `if / else if` 就是在读这些字节。
最后 已写好的代码 要补的那道判断是：
**认出来的大类，必须和声明的 MIME 前缀一致**。

**整个流程的顺序也很关键：**

```text
① 先落到临时目录 .incoming
② 读文件头，确认真实格式
③ 和声明的类型对比，不一致就拒绝并删掉
④ 确认没问题，才改名挪到公开目录
```

**不能先放公开目录再检查**——那中间这段时间文件已经能被外面访问到了。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 备份必须逐字节校验

**为什么做这个**
现在备份只是把文件复制过去。复制到一半断电、磁盘满了、网络盘写坏了——
**全都发现不了**。等到真要恢复时才知道备份是坏的，那时候已经晚了。

**涉及的知识点**

```js
if (digest(source) !== digest(target))
  throw new Error('数据库备份逐字节校验失败')
```

SHA-256 会把整个文件算成一个 64 位十六进制串。
**只要文件有任何一个字节不同，这个串就完全不同**——
不是"有点像"，是完全不同。所以它能可靠地回答"这两个文件一模一样吗"。

注意还有一行是校验 WAL 文件的：

```js
if (existsSync(source + '-wal') && digest(source + '-wal') !== digest(target + '-wal'))
  throw new Error('WAL备份逐字节校验失败')
```

第 09 课打开的 `PRAGMA journal_mode=WAL` 会产生一个 `.sqlite-wal` 文件，
里面是**还没合并进主文件的最新写入**。
**只备份主文件会丢掉最近的数据**——这是个很容易漏的坑。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 算文件摘要的小函数

**为什么做这个**
已写好的代码 用到的 `digest` 函数现在返回空字符串——
`'' !== ''` 永远是 false，**校验形同虚设**。

**涉及的知识点**

```js
const digest = path => createHash('sha256').update(readFileSync(path)).digest('hex')
```

|部分|意思|
|---|---|
|`createHash('sha256')`|创建一个 SHA-256 计算器|
|`.update(readFileSync(path))`|把整个文件内容喂进去|
|`.digest('hex')`|算出结果，输出成十六进制字符串|

## 5. 部署到 Ubuntu 服务器

> 这一节需要一台 Ubuntu 服务器。没有的话看教师演示，
> 完整步骤另见同目录的 `Ubuntu部署实操.md`。

**部署的整体结构：**

```text
公网用户 ──▶ Nginx（80/443）──▶ Node 进程（127.0.0.1:3000）──▶ SQLite 文件
                  │
                  └──▶ 静态文件（dist/）和上传的媒体（var/media/）
```

**为什么要 Nginx 挡在前面？**

|Nginx 负责|Node 负责|
|---|---|
|监听 80/443，处理 HTTPS 证书|业务逻辑和数据库|
|直接返回静态文件（快得多）|只处理 `/api/` 请求|
|限流、压缩、安全响应头|——|

**Node 进程只监听 `127.0.0.1`**，不对外网开放。
这样即使 Node 有漏洞，外面也够不着——**只有 Nginx 能访问它**。

**为什么要 systemd？** 让服务开机自启、崩溃自动重启。
用 `npm run start:api` 手动跑的话，你一关 SSH 窗口进程就没了。

关键命令（在服务器上执行）：

```bash
# 查看服务状态
sudo systemctl status ffd-blog

# 重启服务（改了代码或 .env 之后）
sudo systemctl restart ffd-blog

# 看日志（-f 持续跟着输出）
sudo journalctl -u ffd-blog -f

# 检查 Nginx 配置有没有语法错误，再重载
sudo nginx -t && sudo systemctl reload nginx
```

**上线之后立刻做两件事：**

1. **跑验证脚本**：

```bash
LIVE_BASE=https://你的域名 npm run verify:live
```

2. **手机真机打开一次**。模拟器和真机有差别，这一步不能省。

|`var/media/.incoming` 堆了一堆文件|`finally` 里的清理没执行|检查 `save` 函数的 try/finally|

### 备份与恢复

|现象|原因|处理|
|---|---|---|
|备份报"逐字节校验失败"|正常现象（如果你故意改坏了）|说明校验在工作|
|恢复后数据还是没有|复制的是旧备份，或文件名不对|确认复制的是最新那份，名字要改成 `blog.sqlite`|
|删库时提示文件被占用|后端还在跑|**先停掉后端**（Ctrl+C）再删|
|恢复后少了最近几条数据|只备份了主文件，漏了 `-wal`|`.sqlite-wal` 里有还没合并的最新写入|

### 部署

|现象|原因|处理|
|---|---|---|
|公网打不开，但服务器上 curl 能通|Nginx 没配好，或防火墙挡了|`sudo nginx -t` 检查配置；`sudo ufw status` 看防火墙|
|502 Bad Gateway|Node 进程没起来|`sudo systemctl status ffd-blog` 看状态和报错|
|改了 `.env` 不生效|服务没重启|`sudo systemctl restart ffd-blog`|
|`verify:live` 报数据库不是 SQLite|服务器上的 `.env` 配错了|检查 `DATABASE_PATH`|
|上传的图片重启后没了|部署在了无持久化磁盘的平台上|见 TODO 01 的说明|
