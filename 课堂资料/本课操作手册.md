## 开课前先讲这些概念

学生动手之前，先把这几个词讲清楚。每个只讲到"能用自己的话解释"为止，不展开。

|知识点|小白要理解的话|本课在哪里用到|
|---|---|---|
|自检脚本|一段替你做重复检查的程序。人会累会漏，机器不会|TODO 01—04|
|退出码|程序结束时留下的一个数字。**0 表示成功，非 0 表示失败**|TODO 02、05|
|CI|持续集成。每次推代码，服务器自动跑一遍检查|TODO 05、06|
|CD|持续交付／部署。检查通过后自动发布上线|TODO 05|
|工作流（workflow）|一个 `.yml` 文件，写清楚"什么时候、在哪跑、跑什么"|TODO 05|
|YAML|一种靠**缩进**表示层级的配置格式。**缩进错了就跑不起来**|TODO 05|
|构建产物|要发布出去的那堆文件。本项目是纯静态页，整个目录就是产物|TODO 05|

### 两个最小例子

**例 1：退出码是怎么被用起来的**

```js
if (problems.length) {
  console.log('自检未通过')
  process.exit(1)      // 非 0 → 外面的程序知道"失败了"
}
console.log('自检通过')  // 正常结束，退出码是 0
```

在终端里跑完可以立刻查：

```bat
node tools/check-page.mjs
echo %ERRORLEVEL%
```

打印 `0` 就是通过，`1` 就是没通过。
**GitHub Actions 判断一步成功还是失败，看的就是这个数字。**

**例 2：工作流的三段式**

```yaml
on:                      # 什么时候跑
  push:
    branches: [main]

jobs:                    # 跑什么
  check:
    runs-on: ubuntu-latest   # 在哪跑（GitHub 提供的一台干净的机器）
    steps:
      - uses: actions/checkout@v4     # 把代码下下来
      - run: node tools/check-page.mjs  # 跑自检
```

**这一课要建立的核心观念**：

> **"我这里是好的"不算数，要能证明它在别人那里也是好的。**

你本地能打开，是因为你电脑上有那些文件、有那个文件夹名、有你装的软件。
把代码推上去，在一台**干净的机器**上从头跑一遍，才知道它是不是真的完整。
这就是 CI 存在的全部理由。

### 这一步的常见故障

|现象|原因|处理|
|---|---|---|
|`系统找不到指定的路径`|桌面上还没有 `web-work`|上面第 1 步的 `mkdir` 那两行不能跳过|
|`fatal: repository not found`|仓库地址写错，或仓库是私有的|检查用户名和学号；私有仓库要先登录|
|`fatal: destination path '...' already exists`|这个文件夹已经建过了|换个名字，或先删掉原来那个|
|`dir index.html` 说找不到|`cd` 没进到工程文件夹里|把第 1、2 步的 `cd` 再执行一遍，注意路径最后一段|
|`remote origin does not exist`|`git remote rename` 执行过两次了|跳过这一条，用 `git remote -v` 看现在叫什么|

**`dir` / `Get-ChildItem` 看不到 `index.html` 就不要往下走。** 后面所有步骤都建立在"你在对的文件夹里"这个前提上。

**Windows CMD**

```bat

dir index.html

REM 启动本地服务器（第一次运行会先下载 live-server，要联网，等十几秒）
```

**Windows PowerShell**

```powershell

Get-ChildItem index.html

# 启动本地服务器
npx live-server --port=7000 --host=0.0.0.0
```

**这条命令每个部分是什么意思**：

|部分|作用|
|---|---|
|`npx`|**临时下载并运行**一个命令行工具，用完就好，不用先 `npm install -g` 装到电脑上|
|`live-server`|一个极小的本地网页服务器，**自带热更新**|
|`--port=7000`|服务开在 7000 端口。网址就是 `http://localhost:7000`|
|`--host=0.0.0.0`|**允许同一个局域网里的其他设备访问**（不加只有本机能开）|

### 第三步：确认启动成功

终端里会打印出类似这样的内容：

```text
Serving "E:\...\p1-lesson-06" at http://127.0.0.1:7000
Ready for changes
```

**看到 `Ready for changes` 才算成功。** 浏览器通常会自动打开；
没自动打开就自己访问 <http://localhost:7000>。

**三件事要记住**：

1. **这个终端要一直开着。** 关掉它服务就停了，页面会打不开。
2. **停止服务按 `Ctrl + C`**（在跑着服务的那个终端里按）。
3. **改完代码按 `Ctrl+S` 保存，浏览器会自己刷新**，
   不用再按 `Ctrl+R`。这就是"热更新"。

> 把第二个终端窗口放大一点，输出才看得清。

### 为什么不双击打开 HTML

双击打开时，浏览器地址栏是 `file:///E:/.../index.html`；
用服务器打开是 `http://localhost:7000`。**这两个不是一回事。**

|  |双击打开（file 协议）|本地服务器（http 协议）|
|---|---|---|
|改完代码|**要自己按 `Ctrl+R` 刷新**|**自动刷新**|
|读取本地 JSON、用 `fetch`|**会被浏览器拦住**（跨域限制）|正常|
|`type="module"` 的脚本|**加载不了**|正常|
|`localStorage`|行为和正式环境不一样|和正式环境一致|
|同学能不能看到|不能|**能**，见下面|
|和上线之后的环境|不一样|**几乎一样**|

后面几课会用到 JSON 数据、模块化脚本、本地存储，
**那时候用 file 协议打开会直接报错，而且报的错看起来毫无道理**
（"明明文件就在那儿"）。
**从第一课就用服务器，把这类坑一次性避掉。**

### `--host=0.0.0.0` 能做什么：让同学直接打开你的页面

加了这个参数之后，**同一个局域网里的其他设备可以访问你的页面**——
最实用的就是**用手机看自己做的页面**，尤其是第 03 课的响应式。

**第一步：查自己的局域网 IP**

**Windows CMD**

```bat
ipconfig
```

**Windows PowerShell**

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -like '192.168.*' -or $_.IPAddress -like '10.*' } | Select-Object IPAddress, InterfaceAlias
```

找 `IPv4 地址` 那一行，通常是 `192.168.x.x` 或 `10.x.x.x`。

**第二步：让同学（或你的手机）访问**

```text
http://你的IP:7000
```

比如 `http://192.168.1.23:7000`。**手机要连同一个 Wi-Fi。**

|问题|原因|处理|
|---|---|---|
|同学打不开|Windows 防火墙挡了|第一次启动时弹出的提示要选「允许访问」；已经点了拒绝就到「防火墙 → 允许应用」里放行 Node|
|手机打不开|不在同一个 Wi-Fi|确认手机和电脑连的是同一个网络，机房有时分了好几个网段|
|IP 有好几个|有虚拟网卡（VMware、WSL）|用 `192.168.` 开头那个通常没错，不行就一个个试|

> **安全提示**：`0.0.0.0` 的意思是"对本机所有网卡开放"。
> 在教室和家里的局域网没问题，**但不要在公共 Wi-Fi（咖啡馆、机场）下这么开**。
> 只想自己用的时候，把参数去掉就行：`npx live-server --port=7000`。

### 启动不起来怎么办

|终端里报什么|原因|处理|
|---|---|---|
|`'npx' 不是内部或外部命令`|Node 没装，或装完没重开终端|装 Node 24，**关掉所有终端重开**；再 `node -v` 确认|
|卡在下载不动|npm 源慢|`npm config set registry https://registry.npmmirror.com` 之后重试|
|`EADDRINUSE` / 端口被占用|7000 已经被别的程序占了（**多半是你自己上一次没关**）|换一个端口：`--port=7001`；或者到之前那个终端按 `Ctrl+C`|
|浏览器显示目录列表，不是页面|工程根目录里没有 `index.html`|`dir index.html` 确认位置，`cd` 到对的目录重来|
|页面打开了但一片空白|HTML 里有错，或者文件名拼错|`F12` → Console 看红字；确认文件名大小写|
|改了代码不自动刷新|文件没保存；或者改的不是这个目录里的文件|`Ctrl+S`；确认 Trae 打开的文件夹和终端所在的是同一个|

**实在起不来也别耽误上课**：先双击 `index.html` 应急，
本课绝大部分内容照样能做，**下课前再来解决**。

### TODO 01 · 本地跑一次自检

**难度**：极简单


**为什么做这个**
在改任何东西之前，先确认**现在是好的**。
不然改完出了问题，你分不清是本来就坏的还是刚弄坏的。

**涉及的知识点**

`tools/check-page.mjs` 这个脚本做三件事，都是人工检查很容易漏、机器检查很快的：

|检查项|它在找什么|人工为什么容易漏|
|---|---|---|
|必须有的文件|`index.html` / `styles.css` / `app.js` 在不在|本地都在，提交时漏了才发现|
|本地引用|HTML 里引用的 css、js、图片是不是真的存在|路径错一个字母，页面上可能只是少一张图|
|页内锚点|`href="#skills"` 有没有对应的 `id="skills"`|点了没反应，但不报错|

**改哪里**：不用改代码，在**工程根目录**执行命令。

**Windows CMD**

```bat
node tools/check-page.mjs
```

**Windows PowerShell**

```powershell
node tools/check-page.mjs
```

**操作前 / 操作后**

- 操作前：你只能靠肉眼一遍遍看页面，不知道有没有坏引用。
- 操作后：终端里一串 `[OK]`，最后一行「**自检通过。**」

**自己验证**
1. 输出里能看到三段（或四段，做完 已写好的代码 之后）检查标题。
2. 立刻查退出码：

**Windows CMD**

```bat
echo %ERRORLEVEL%
```

**Windows PowerShell**

```powershell
$LASTEXITCODE
```

应该打印 `0`。**记住这个数字，TODO 02 会看到它变成 1。**

**多想一步**
为什么这个脚本一个第三方包都不用？
因为**依赖越少，越不容易坏**。要装包就要联网、要对版本、要占空间，
而这三件检查用 Node 自带的 `fs` 和正则就够了。
**能不加依赖就不加**，这是工程上的一条通用判断。

### TODO 02 · 故意弄坏一处，看自检报错

**难度**：极简单


**为什么做这个**
**一个从来没报过错的检查，等于没有检查。**
你必须亲眼确认它真的能抓到问题，才敢信任它。

这个思路在测试里有个名字，叫"**让测试先失败**"——
先制造一个它应该抓到的问题，确认它抓到了，再修好。

**涉及的知识点**

自检脚本能抓三类问题，挑一类来制造：

|制造什么|怎么改|脚本会说什么|
|---|---|---|
|坏的文件引用|把某个 `src="assets/xxx.png"` 改成 `xxx-typo.png`|`引用了不存在的文件`|
|坏的锚点|把某个 `href="#skills"` 改成 `#skill`|`导航指向 #skill，但页面里没有 id`|
|缺文件|把 `app.js` 临时改名|`缺少 app.js`|

**改哪里**：`index.html`，挑上面任意一种改一处。**记住你改了哪里。**

**操作前 / 操作后**

- 操作前：自检全绿，最后一行「自检通过。」，退出码 `0`。
- 操作后：出现一行**红色的 `[X]`**，指出具体是哪个文件／哪个锚点，
  最后一行变成「自检未通过，共 1 个问题」，**退出码变成 1**。

**自己验证**
1. 改完立刻跑 `node tools/check-page.mjs`，确认 `[X]` 出现了。
2. 查退出码，应该是 `1`。
3. **打开浏览器看页面**——很多时候页面**看起来还好好的**
   （比如少一张图，你可能都没注意）。
   **这就是为什么需要机器检查：人眼对"少了点什么"非常不敏感。**

**多想一步**
把这条错误的信息读一遍：它有没有告诉你**具体是哪个文件**？
好的错误信息应该让人**不用再去猜**。
已写好的代码 你自己写检查时，记住这一点。

### TODO 03 · 修好它，让自检回到全绿

**难度**：简单


**为什么做这个**
形成完整的闭环：**发现问题 → 定位 → 修复 → 再验证**。
这一步看着简单，但"改完一定要重新跑一遍"是个需要刻意养成的习惯。

**改哪里**：把 TODO 02 改坏的地方改回去。

**操作前 / 操作后**

- 操作前：自检有一条 `[X]`，退出码 `1`。
- 操作后：自检全绿，「自检通过。」，退出码回到 `0`。

**自己验证**
1. 跑自检，确认没有 `[X]`。
2. 查退出码，是 `0`。
3. `git status` 看一眼——**改动应该已经全部撤销，工作区是干净的**。
   如果还有改动，说明你改回去的时候没改彻底。

**多想一步**
`git diff` 在这里比肉眼可靠得多：它会逐行告诉你现在和上次提交差在哪。
**养成"修完用 `git diff` 确认只改了该改的地方"的习惯**，
可以避免一大类"顺手改坏了别的东西"的事故。

### TODO 04 · 手机与打印检查

**难度**：简单

**改哪里**：**这一个任务不改代码**，全部在浏览器里操作——
`F12` 打开开发者工具 → 左上角的**手机图标**（设备工具栏）切换手机尺寸；
`Ctrl + P` 打开**打印预览**。发现问题再回到 `styles.css` 里改。


**为什么做这个**
自检脚本查的是"文件和引用对不对"，**它查不出"好不好看"**。
有两种场景必须用眼睛看：**手机屏**和**打印／导出 PDF**。

个人主页很可能被打印成 PDF 投简历，所以打印效果不能崩。

**涉及的知识点**

|检查项|怎么做|要看什么|
|---|---|---|
|手机|F12 → 左上角手机图标 → 选 iPhone|有没有横向滚动条；字会不会太小；按钮好不好点|
|平板|同上，选 iPad|两列还是一列，会不会尴尬地卡在中间|
|打印|`Ctrl+P` 打开打印预览|导航和浮层会不会占地方；内容会不会被切断|
|真机|手机浏览器打开你的 Pages 地址|**这一步不能省**，模拟器和真机有差别|

**操作前 / 操作后**

- 操作前：只在电脑全屏看过，不知道手机和打印是什么样。
- 操作后：三种尺寸都确认过，打印预览里内容完整。

**自己验证**
1. F12 手机模拟器，切 iPhone SE（最窄的常见尺寸）、iPhone 14、iPad 各看一遍。
2. **横向滚动条是重点**：任何宽度下都不该出现。有的话回第 03 课检查 `minmax(0, 1fr)`。
3. `Ctrl+P` 打开打印预览，看进度条、返回顶部按钮、筛选工具条
   **有没有被打印出来**——它们在纸上没有意义。
4. 如果被打印出来了，在 `styles.css` 末尾加一段：

```css
@media print {
  .reading-progress,
  .section-indicator,
  .to-top,
  .works-toolbar { display: none; }
}
```

**多想一步**
`@media print` 和第 03 课的 `@media (max-width: 640px)` 是同一类东西——
**媒体查询不只能查屏幕宽度，还能查"输出到什么介质"。**
一个正经的网站通常都会写一段打印样式，把导航、广告、按钮全部隐藏掉。

### TODO 05 · 启用 GitHub Actions：推代码就自动检查并发布

**难度**：中等


**为什么做这个**
前五个任务都是"你记得去做"。但人会忘。
**把检查交给机器，让它在每次推代码时自动跑**，才是真正可靠的。

同时它还解决一件事：以前你要手动去仓库 Settings 里开 Pages，
现在**检查通过后自动发布**。

**涉及的知识点：工作流文件**

打开 `.github/workflows/pages.yml` 对着看：

```yaml
on:                         # ① 什么时候跑
  push:
    branches: [main]        #    往 main 推的时候
  workflow_dispatch:        #    也允许手动点按钮触发

jobs:
  check:                    # ② 第一个任务：自检
    runs-on: ubuntu-latest  #    在 GitHub 提供的一台干净 Ubuntu 上跑
    steps:
      - uses: actions/checkout@v4      # 把你的代码下下来
      - uses: actions/setup-node@v4    # 装 Node
        with:
          node-version: '24'
      - run: node tools/check-page.mjs # 跑自检

  deploy:                   # ③ 第二个任务：发布
    needs: check            #    **必须等 check 成功**才开始
    ...
```

|关键词|意思|
|---|---|
|`on`|触发条件|
|`jobs`|要做的几件事，默认并行|
|`needs: check`|依赖。check 失败，deploy **根本不会开始**|
|`runs-on`|在什么机器上跑|
|`uses`|用别人写好的现成动作|
|`run`|直接执行一条命令|

**`needs: check` 这一行是整个文件的关键**：它保证了**没通过检查的代码不会被发布出去**。

**YAML 靠缩进表示层级，缩进错了整个文件就废了。** 改的时候注意对齐，
**不要用 Tab，只用空格**。

**改哪里**：文件不用改，但要做三件事把它启用起来：

1. **确认文件在**：`dir /a .github`（CMD）或 `Get-ChildItem .github -Force`（PowerShell）。
2. **改仓库的 Pages 来源**：仓库 → `Settings` → `Pages` →
   Source 从 `Deploy from a branch` 改成 **`GitHub Actions`**。
3. **提交并推送**（见第 6 节）。

**操作前 / 操作后**

- 操作前：每次改完要自己记得跑自检，自己去点发布。
- 操作后：`git push` 之后，仓库页面提交记录旁边出现一个**转圈的黄点**，
  一两分钟后变成**绿色对勾 ✓**，网站自动更新。

**自己验证**
1. 推送后打开仓库页面，提交记录右边有个小圆点。
2. 点顶部 **Actions** 标签，能看到这次运行，点进去能看到 `check` 和 `deploy` 两步。
3. 展开 `check` 里的「检查文件、引用和锚点」，**能看到和你本地一模一样的 `[OK]` 输出**。
4. 等 `deploy` 也变绿，打开你的 Pages 地址，**内容是最新的**。

**多想一步**
为什么要在一台"干净的机器"上重跑一遍？
因为你本地能跑通，可能是因为你电脑上有某个文件、某个软件、某个环境变量。
**CI 上那台机器只有你提交进仓库的东西。**
所以 CI 通过 = "任何人克隆你的仓库都能跑通"，这才是真正的保证。
这也解释了一个经典现象：「在我这儿是好的啊」——那句话在 CI 面前没有意义。

### TODO 06 · 让 CI 抓一个真 bug

**难度**：中等


**为什么做这个**
和 TODO 02 同一个道理：**一个从来没亮过红灯的 CI，你不知道它是不是真的在工作。**
必须亲眼看它拦一次。

**这一步一定要做**，它是本课最有说服力的一个瞬间。

**涉及的知识点**

整个链条走一遍：

```text
你改坏一处 → git push → GitHub 起一台干净机器 → 下代码 → 跑自检
  → 脚本发现问题 → process.exit(1) → 这一步失败
  → check 任务红叉 → deploy 因为 needs: check **根本不会运行**
  → 网站保持旧版本不动 → GitHub 给你发邮件
```

**注意"网站保持旧版本不动"这一点**：CI 不只是提醒你，
它**挡住了一次把坏页面发布上线的事故**。

**改哪里**：随便挑一处改坏（和 TODO 02 一样），然后推上去。

```bat
REM 故意改坏 index.html 里某个图片路径，然后
git add .
git commit -m "演示：故意提交一个坏引用"
git push origin main
```

**操作前 / 操作后**

- 操作前：你只知道"CI 会跑"，但没见过它拦住什么。
- 操作后：仓库页面出现**红色叉号 ✗**，点进去能看到**具体哪一行报的错**；
  邮箱收到一封失败通知；**Pages 上的网站还是上一个好版本**。

**自己验证**
1. 推上去后进 Actions，看到红叉。
2. 点进去展开失败那一步，**能看到 `[X]` 那一行**，和你本地看到的一样。
3. 打开 Pages 地址，**页面还是好的**——坏版本没有被发布。
4. 检查邮箱，GitHub 会发一封 "run failed" 通知。
5. **修好再推一次**：

```bat
REM 把改坏的地方改回去
node tools/check-page.mjs        REM 本地先确认通过
git add .
git commit -m "修复：还原坏引用"
git push origin main
```

6. 回 Actions，这一次应该是**绿勾**，网站也更新了。

**多想一步**
这一轮"红 → 修 → 绿"就是真实团队每天在做的事。
它背后是一条纪律：

> **主分支上的代码，任何时候都应该是可用的。**

所以才要在合并之前跑检查、在发布之前跑检查。
本课只有一个人一个分支，看不出威力；
但想象二十个人往同一个仓库推代码——**没有 CI，主分支很快就会坏掉，
而且没人知道是谁弄坏的。**

### 已写好 · 给自检脚本加一条新检查

**为什么做这个**
前三个任务你都在**用**别人写好的工具。这一个要**扩展**它。

要加的检查是：**所有 `<img>` 都必须有写清楚内容的 `alt`。**
选这一条是因为它非常典型——`alt` 很容易在改代码时被删掉，
而且**页面看起来完全正常**，人工根本发现不了。

**涉及的知识点**

```js
// 1) 把所有 <img ...> 标签取出来
const imgs = [...html.matchAll(/<img[^>]*>/g)].map(m => m[0])

// 2) 每个都看看有没有 alt="非空内容"
const found = tag.match(/alt="([^"]*)"/)
```

|写法|作用|
|---|---|
|`matchAll(正则)`|找出**所有**匹配，返回一个迭代器|
|`[...迭代器]`|展开成数组|
|`/<img[^>]*>/g`|`[^>]*` 表示"除了 `>` 之外的任意字符"，`g` 表示全局找|
|`match(正则)`|找第一个匹配，返回数组或 `null`|

要判断三种不合格的情况：**没有 `alt`**、**`alt` 是空的**、
**`alt` 写得太笼统**（只写"图片""照片"这类没信息量的词）。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

## 6. Git 提交与推送

### 第一步：提交前先在本地跑一遍自检

**这是本课新增的纪律，从今往后每次提交都该这么做。**

```bat
node tools/check-page.mjs
```

**不通过就不要提交。** 推上去 CI 一样会拦下来，白白浪费一轮等待。

### 第二步：看清楚自己改了什么

```bat
git status
git diff
```

确认列表里只有你改的文件，没有临时文件和无关文件。

### 第三步：提交并推送

```bat
git add .
git commit -m "P1第06课：自检脚本、移动端与打印检查、CI/CD 自动发布"
git push origin main
```

**推送报 `'origin' does not appear to be a git repository` 怎么办？**
本课工程是从上一课或教师模板克隆来的，来源已经被改名成 `previous` / `course`
（那是别人的仓库，不能推）。先到 GitHub 新建一个空仓库 `p1-lesson-06-学号`
（新建时**不要**勾选 "Add a README file"），然后：

**Windows CMD**

```bat
git remote add origin https://github.com/你的用户名/p1-lesson-06-学号.git
git branch -M main
git push -u origin main
git remote -v
```

**Windows PowerShell**

```powershell
git remote add origin https://github.com/你的用户名/p1-lesson-06-学号.git
git branch -M main
git push -u origin main
git remote -v
```

### 第四步：把 Pages 的来源改成 GitHub Actions

**这一步和前五课不一样，务必看清。**

1. 打开仓库页面 → 顶部 `Settings` → 左侧 `Pages`。
2. Source 从 `Deploy from a branch` 改成 **`GitHub Actions`**。
3. 不用选分支，也不用点 Save——选完就生效。

改完之后，**发布由 `.github/workflows/pages.yml` 接管**：
每次推代码自动跑检查，通过了自动发布。

### 第五步：确认这一轮走通了

1. 仓库页面 → `Actions` 标签 → 看到最新一次运行。
2. `check` 和 `deploy` 两步都是绿勾。
3. 打开 Pages 地址（Actions 的 deploy 步骤里会显示网址），内容是最新的。

## 常见问题

### 自检脚本

|现象|原因|处理|
|---|---|---|
|`'node' 不是内部或外部命令`|Node 没装，或装完没重开终端|到 <https://nodejs.org/> 装 Node 24，**装完关掉所有终端重开**|
|`Cannot find module` / 找不到脚本|不在工程根目录|先 `cd` 到有 `index.html` 的那一层再跑|
|报了一堆 `引用了不存在的文件`|路径大小写不一致，或文件真的没了|Windows 不区分大小写、服务器区分，按报错逐个核对|
|锚点报错但页面能跳|`id` 里有多余空格，或写成了 `class`|F12 → Elements 找到那个元素确认|
|已写好的代码 写完脚本报语法错|正则里的斜杠或引号没配对|`node --check tools/check-page.mjs` 能单独查语法|

### GitHub Actions

|现象|原因|处理|
|---|---|---|
|推了之后 Actions 里什么都没有|`.github` 目录没提交上去|`git status` 看；隐藏目录容易漏，用 `git add .github` 显式加|
|`check` 一直失败，本地却通过|本地有的文件没提交|CI 上只有仓库里的东西，`git status` 看有没有漏|
|`deploy` 报权限错误|Pages 来源没改成 GitHub Actions|Settings → Pages → Source 选 `GitHub Actions`|
|`deploy` 被跳过|`check` 失败了|`needs: check` 决定的，先修好检查|
|YAML 报语法错|缩进用了 Tab，或对齐不一致|YAML **只能用空格**，同一层级必须对齐|
|Pages 地址打开是 404|第一次发布还没完成|等 Actions 全绿之后再等一两分钟|
|网站没更新|浏览器缓存|按 `Ctrl+F5` 强制刷新|

### 提交

|现象|原因|处理|
|---|---|---|
|`git push` 报 `'origin' does not appear...`|来源已改名成 previous / course|见第 6 节第三步|
|`.github` 没被提交|有些工具默认忽略点开头的目录|`git add .github` 显式添加，再 `git status` 确认|
|提交了但 Actions 没触发|推到了别的分支|工作流只监听 `main`，用 `git branch` 看当前分支|

更多通用排错见 `通用附录_运行与排错.md`；
命令和参数的逐条解释见 [命令参数逐个拆开](<../../01_入门与通用规范/04_命令参数逐个拆开.md>)。
