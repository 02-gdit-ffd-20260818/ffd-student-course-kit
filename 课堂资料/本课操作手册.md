## 本课在项目 3 里的位置

第 12 课把数据存在一个 `db.json` 文本文件里。你亲手写了三段检查：
邮箱不能重复、班级必须存在、密码要对。而且发现了两个根本问题——
**每次写入都要重写整个文件**，**两个人同时写会互相覆盖**。

这一课换成**真正的数据库**。你会看到：其中一大半检查可以**交给数据库自动完成**，
而且它天生就能处理"只改一行"和"多人同时写"。

|课次|工程|数据存在哪|这一课新出现的问题|
|---|---|---|---|
|12|`PersonaLink_NoDB`|一个 `db.json` 文本文件|并发写会互相覆盖；没有任何约束|
|13|`PersonaLink_SQLite`|一个 `.sqlite` 文件（Node 24 内置）|约束、外键、事务交给数据库|
|14|`PersonaLink_MySQL`|独立运行的 MySQL 服务|第一次有账号密码；密码不能明存|
|15|`PersonaLink_Docker`|PostgreSQL 容器 + 数据卷|环境怎么一键复制；数据怎么不跟着容器消失|

**四课做的是同一个产品**——界面、接口、功能完全一样，
差别只在**数据存在哪、怎么存**。所以这四课最值得记住的不是某一种数据库的语法，
而是：**换一种存储，同一件事该怎么做、代价是什么。**


**这一课用的是 Node 24 内置的 `node:sqlite`**——不用装任何第三方包，
不用启动任何服务，数据库就是一个文件。
这是"从文本文件到数据库"最平滑的一步。

## 开课前先讲这些概念

|知识点|小白要理解的话|本课在哪里用到|
|---|---|---|
|SQL|操作数据库的语言。`SELECT` 查、`INSERT` 增、`UPDATE` 改、`DELETE` 删|全课|
|建表|先声明"这张表有哪些列、每列什么规矩"，再往里存数据|TODO 01、02|
|约束|写在建表语句里的规则，**数据库自己会挡住不合规的数据**|TODO 01、02|
|外键|一列的值必须在**另一张表**里真实存在|TODO 02|
|`PRAGMA`|SQLite 的开关设置，**每个连接都要重设一遍**|已写好的代码|
|事务|一批操作**要么全成功、要么全不发生**，没有中间状态|已写好的代码|
|WAL|一种日志模式，让读和写不互相阻塞|TODO 04|

### 对照着第 12 课看：同一件事，两种做法

|要保证的事|第 12 课（JSON 文件）|第 13 课（SQLite）|
|---|---|---|
|邮箱不重复|自己写 `find` 查一遍|`email TEXT NOT NULL UNIQUE`|
|班级必须存在|自己写 `find` 查一遍|`class_id TEXT REFERENCES classes(id)`|
|名字不能为空|自己写 `if`|`name TEXT NOT NULL`|
|一批写入不能写一半|**做不到**|事务 `BEGIN / COMMIT / ROLLBACK`|
|两个人同时写|**会互相覆盖**|数据库自己处理|

**左边那一列你上节课全都手写过了。** 现在看右边——大部分变成了一行声明。

**这就是数据库的价值：把"保证数据正确"这件事，从代码里搬进数据本身。**
代码可能有别的入口绕过去（另一个接口、一个脚本、有人直接改文件），
约束没有——**不管从哪写，都绕不过**。

### 一个最小例子：约束是怎么挡住你的

```sql
CREATE TABLE users (
  id    TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE
);

INSERT INTO users VALUES ('1', 'a@x.com');   -- 成功
INSERT INTO users VALUES ('2', 'a@x.com');   -- 失败：UNIQUE constraint failed
INSERT INTO users VALUES ('3', NULL);        -- 失败：NOT NULL constraint failed
```

**不用写一行 JavaScript**，数据库自己拒绝了。

|终端里报什么|原因|处理|
|---|---|---|
|`'npm' 不是内部或外部命令`|Node 没装，或装完没重开终端|装 Node 24，**关掉所有终端重开**，再 `node -v` 确认|
|`Cannot find module`|依赖没装，或者不在工程目录里|先确认当前目录对不对，再 `npm install`|
|`EADDRINUSE` 端口被占用|**多半是上一次的服务没关**|找到那个终端按 `Ctrl+C`；或者换个端口|

### TODO 01 · 给 users 表加上约束

**难度**：极简单


**为什么做这个**
**这是本课最能体会"数据库替你干活"的一步。**

第 12 课 TODO 02 你写了一段 `find` 来查重复邮箱。

**涉及的知识点**

|约束|作用|第 12 课对应的是|
|---|---|---|
|`PRIMARY KEY NOT NULL`|主键唯一，并显式禁止 NULL；SQLite 普通表的 TEXT 主键不能省略这一点|（当时没做）|

### TODO 02 · 班级外键

**难度**：简单


**为什么做这个**
第 12 课 已写好的代码 你写了一段"检查班级是否存在"。
数据库可以自动做这件事，而且还能做得更多——**反过来保护班级不被误删**。

**涉及的知识点**

```sql
class_id TEXT REFERENCES classes(id) ON DELETE RESTRICT
```

|部分|意思|
|---|---|
|`REFERENCES classes(id)`|这一列的值**必须在 classes 表的 id 里存在**|
|`ON DELETE RESTRICT`|被指向的班级**只要还有人在用，就不许删**|

**和项目 2 第 09 课的 `ON DELETE CASCADE` 对照着看：**

|场景|用哪个|为什么|
|---|---|---|
|文章被删，它的评论|`CASCADE` 连带删除|评论脱离文章没有意义|
|班级被删，班里的学生|`RESTRICT` 拦住不让删|**学生不该跟着班级一起消失**|

**选哪个取决于业务含义，不是技术偏好。** 这是本课一个重要的判断练习。

**改哪里**：`backend/src/database.js` 的 `class_id` 那一列，TODO 02 的位置。

1. `npm run db:status` → 「日志模式: wal」。
2. **看一眼 `backend/data/` 目录**：

**Windows CMD**

```bat

```

**Windows PowerShell**

```powershell
Get-ChildItem backend\data
```

连接活跃时可能看到 `.sqlite-wal` 和 `.sqlite-shm`；所有连接正常关闭后它们可能消失，这是正常现象。以查询到的日志模式为准。

**多想一步：这一课的备份有个坑**

`.sqlite-wal` 里装的是**还没合并进主文件的最新写入**。

所以**只复制 `.sqlite` 主文件会丢掉最近的数据**——
而且丢得很隐蔽：备份看起来成功了，恢复之后发现少了最后几条。

**使用提供的快照工具，不在运行中逐个复制这些文件。** 只执行一次 checkpoint 后仍可能有新写入；分开复制三个文件也不保证同一时刻的一致状态。

在工程根目录先进入后端目录，然后执行（两种 Windows 终端相同）：

```text
cd backend
node scripts/backup-sqlite.js data/backup-lesson13-01.sqlite
cd ..
```

最后一个参数是备份目标路径，以 `backend` 为起点。目标必须不存在，已有则换名字，不要覆盖。
工具按 `.env` 的 `DATABASE_PATH` 读取源库，用 SQLite 的 `VACUUM INTO` 生成包含已提交数据的一致副本，
再执行 `integrity_check`（数据库内部完整性检查），显示 `ok` 和用户行数。源文件不会删除。

**恢复演练**：在 Navicat 新建 SQLite 连接，打开备份文件，检查班级、用户及最近新增的一条资料。
需要验证应用读取时，先停止后端，记录原 `DATABASE_PATH`，将它临时改为备份路径，再运行 `npm run db:status`；
确认路径和数量对应，测试后恢复原配置。不要把备份覆盖回原库，也不要求先删除原库。

依据：[SQLite 官方备份说明](https://www.sqlite.org/backup.html)、[WAL 文档](https://www.sqlite.org/wal.html)。

### 已写好 · 打开外键检查和 WAL

**为什么做这个**
**这是本课最大的一个坑。**

你在 TODO 02 里写的 `REFERENCES` 和 `ON DELETE RESTRICT`，
如果不打开这个开关，SQLite **一条都不会执行**——
建表语句照收不误、不报任何错，但运行时**完全不检查**。

很多人会花半小时怀疑自己外键写错了，其实语法完全正确，只是开关没开。

**涉及的知识点**

```js
database.exec('PRAGMA journal_mode = WAL')
database.exec('PRAGMA foreign_keys = ON')
database.exec('PRAGMA busy_timeout = 5000')
database.exec('PRAGMA synchronous = NORMAL')
```

|PRAGMA|作用|
|---|---|
|`foreign_keys = ON`|**打开外键检查**（本课重点）|
|`journal_mode = WAL`|读写并发更好：**读的时候不挡写，写的时候不挡读**|
|`busy_timeout = 5000`|数据库被占用时最多等 5 秒再报错，而不是立刻失败|
|`synchronous = NORMAL`|写入的安全级别。FULL 最安全但最慢，NORMAL 是常用折中|

**`PRAGMA` 是"每个连接"的设置，不是存在数据库文件里的。**
所以每次建立连接都要重新执行一遍——这正是它写在建立连接那一步的原因。

**WAL 改善读写并发，但不能单独解决业务层覆盖**：
默认模式下写入时整个数据库被锁住，读也进不来；
WAL 把新写入记到日志里，让读者可继续读快照；写操作仍需协调。本工程采用内存集合整体写回，仅适合单个后端进程的课堂演示，不能因此宣称多进程不会覆盖数据。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 用事务包住这一批写操作

**为什么做这个**
导入种子数据要往三张表里写几十条记录。
**万一写到一半出错（某条数据格式不对、磁盘满了、进程被杀），前面已经写进去的怎么办？**

**涉及的知识点**

```js
database.exec('BEGIN')       // 开始事务
// ……一批写入……
database.exec('COMMIT')      // 全部生效
// 或
database.exec('ROLLBACK')    // 全部撤销，像什么都没发生过
```

|  |不用事务|用事务|
|---|---|---|
|写到一半出错|**一半数据在库里、一半没有**，而且你不知道是哪一半|**全部撤销**，数据库回到操作之前的样子|
|数据库的状态|"半成品"，无法判断该从哪继续|要么完整、要么原样，**没有中间状态**|

**这个特性叫"原子性"**：一批操作像一个不可分割的原子，
要么整个发生，要么整个不发生。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

### 已写好 · 提交或回滚

**为什么做这个**
事务有始必有终，而且**只有两种结局**。漏掉任何一种都会出问题。

**涉及的知识点**

```js
try {
  database.exec('BEGIN')
  // ……一批写入……
  database.exec('COMMIT')      // 成功：全部生效
} catch (error) {
  database.exec('ROLLBACK')    // 失败：全部撤销
  throw error                  // 再把错误抛出去，让调用方知道
}
```

**漏掉 `ROLLBACK` 会怎样？** 这是个很隐蔽也很严重的问题：

出错时事务一直开着，**数据库会一直锁着相关的行**，
后面所有请求都卡在那里等——表现出来就是"**网站突然全卡死了**"，
而且日志里可能什么异常都没有。查起来非常费劲。

注意 `catch` 里 `ROLLBACK` 之后还要 `throw error`。
不抛的话，错误被"吃掉"了，调用方以为一切正常。

> 这段代码工程里**已经写好了**。打开对应文件，找到这一段读一遍注释，
> 知道它在做什么、为什么这么写即可，**不用动手改**。

## 常见问题

### 建表与约束

|现象|原因|处理|
|---|---|---|
|**改了建表语句没生效**|`CREATE TABLE IF NOT EXISTS` 不改已有的表|**停止后端，改用未使用的 DATABASE_PATH，保留旧库**；不能只改代码继续连旧表|
|**外键完全不起作用**|没打开 `PRAGMA foreign_keys = ON`|见 已写好的代码，本课最大的坑|
|`UNIQUE constraint failed`|违反了唯一约束|正常现象，说明约束在工作|
|`FOREIGN KEY constraint failed`|指向了不存在的行，或删了还在被引用的行|正常现象；看是哪一条数据的问题|
|`NOT NULL constraint failed`|某个必填列是空的|检查种子数据或注册表单|

### 数据

|现象|原因|处理|
|---|---|---|
|**换了 seed.json 数据没变**|SQLite 只在首次运行时导入种子|保留旧库并改用新的 DATABASE_PATH，见第 2 节第三步|
|`db:status` 报"先启动"|数据库文件还没生成|先把后端跑起来，首次启动会自动建库|
|路线 A 搬完数据条数不对|复制到了别的地方，或文件大小没变|回第 2 节第二步，用 `dir` 确认文件大小|
|导入失败后再跑就卡住|事务没回滚，数据库被锁|停止重复启动的进程并关闭 Navicat 连接，查看最先出现的错误；不要删库|

### 启动

|现象|原因|处理|
|---|---|---|
|`node:sqlite` 找不到|Node 不是 24|`node -v` 确认；本课程统一 Node 24|
|页面空白|终端 1 的后端没起来|回终端 1 执行 `npm run dev:backend`|
|`EADDRINUSE`|端口被占用|关掉所有终端重来|
|`database is locked`|另一个进程正占着数据库|关掉其它终端；`busy_timeout` 也能缓解|

更多通用排错见 `通用附录_运行提交部署与排错.md`；
命令和参数的逐条解释见 [命令参数逐个拆开](<通用/04_命令参数逐个拆开.md>)。
