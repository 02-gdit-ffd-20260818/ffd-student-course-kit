## 本课在项目 3 里的位置

项目 3 只做**一个产品**：群像云图——一个班级同学的照片墙，
能注册、能填个人资料、能按班级和爱好查人。

但这一个产品要做**四遍**，每一遍换一种存储方式：

|课次|工程|数据存在哪|这一课新出现的问题|
|---|---|---|---|
|12|`PersonaLink_NoDB`|一个 `db.json` 文本文件|并发写会互相覆盖；没有任何约束|
|13|`PersonaLink_SQLite`|一个 `.sqlite` 文件（Node 24 内置）|约束、外键、事务交给数据库|
|14|`PersonaLink_MySQL`|独立运行的 MySQL 服务|第一次有账号密码；密码不能明存|
|15|`PersonaLink_Docker`|PostgreSQL 容器 + 数据卷|环境怎么一键复制；数据怎么不跟着容器消失|

**四课做的是同一个产品**——界面、接口、功能完全一样，
差别只在**数据存在哪、怎么存**。所以这四课最值得记住的不是某一种数据库的语法，
而是：**换一种存储，同一件事该怎么做、代价是什么。**


**这一课是四遍里的第一遍**：数据存在一个 `db.json` 文本文件里。
它是最简单的做法，也是**问题最多的做法**——正因为如此，
你会在这一课亲手写下后面三课由数据库自动完成的那些事。

## 开课前先讲这些概念

|知识点|小白要理解的话|本课在哪里用到|
|---|---|---|
|前后端分离|页面（5173）和接口（3001）是两个独立进程，靠 HTTP 说话|第 3 节|
|REST 接口|后端对外提供的一个网址 + 方法，比如 `GET /api/users`|全课|
|JSON|一种文本格式，长得像 JavaScript 对象，人和机器都能读|全课|
|持久化|数据写进文件或数据库，**进程退出后还在**|TODO 03|
|解构赋值|`const { a, ...rest } = obj`——挑出一部分，剩下的收进另一个变量|TODO 05|
|孤儿记录|指向一个不存在的东西的数据|已写好的代码|

### 这一课要建立的核心观念

> **"能存下来"和"存得对"是两件完全不同的事。**

JSON 文件能存下任何东西——包括重复的邮箱、指向不存在班级的用户、
一个只有空格的名字。它不会拦你，因为**它只是一段文本**。

所有的检查，这一课都得你自己写。第 13 课换成数据库之后，
其中一大半可以交给数据库自动完成。
**做完这一课，你才会知道数据库到底替你做了多少事。**

### 一个最小例子：JSON 文件当数据库是什么样

```js
// 读：把整个文件读进内存，变成一个大对象
const db = await connectDB()
console.log(db.data.users.length)    // 43

// 改：改的是内存里的数组
db.data.users.push(newUser)

// 写：把整个对象重新写回文件
await db.write()
```

**注意"整个"这两个字**：每次写入都要把**全部数据**重新写一遍。
43 条数据无所谓，4300 条就明显卡了，43 万条根本没法用。
而且**两个人同时写会互相覆盖**——后写的那个把前一个的改动整个盖掉。

这就是为什么真实系统要用数据库：它能**只改那一行**，还能处理并发。

**停止服务**：在跑着它的那个终端里按 `Ctrl + C`。
按一次没反应就再按一次，Windows 上偶尔会问 `终止批处理操作吗(Y/N)?`，输 `Y` 回车。

**改了代码要不要重启？**

|改什么|要不要手动重启|
|---|---|
|前端代码（页面、组件、样式）|**不用**，保存后浏览器自动刷新|
|后端代码|**不用**，`--watch` / `nodemon` 会自动重启|
|`.env` 里的配置|**要**，环境变量只在启动时读一次|
|`package.json` 的依赖|**要**，而且要先 `npm install`|

### 启动不起来怎么办

|终端里报什么|原因|处理|
|---|---|---|
|`'npm' 不是内部或外部命令`|Node 没装，或装完没重开终端|装 Node 24，**关掉所有终端重开**，再 `node -v` 确认|
|`Cannot find module`|依赖没装，或者不在工程目录里|先确认当前目录对不对，再 `npm install`|
|`EADDRINUSE` 端口被占用|**多半是上一次的服务没关**|找到那个终端按 `Ctrl+C`；或者换个端口|
|`npm ci` 报 lock 文件对不上|`package.json` 改过但没更新 lock|先 `npm install` 生成新的 lock，再提交|
|装依赖卡住不动|npm 源慢|`npm config set registry https://registry.npmmirror.com` 再重试|
|页面能打开但数据是空的|**后端没起来**|F12 → Network，看那条请求是红的还是 200|
|一片空白，Console 全是红字|前端代码有错|从 **第一条**报错开始看，不要直接翻到最后|

### TODO 01 · 让照片墙有数据

**难度**：极简单


**为什么做这个**
**这是本课最直观的一步。** 做之前照片墙一片空白，做完全班同学都出来了。

**涉及的知识点**

```js
const db = await connectDB()
const allUsers = db.data.users.map(user => formatUserData(user, db))
res.json(allUsers)
```

|部分|作用|
|---|---|
|`await connectDB()`|读 `db.json`，返回 `{ data, write }`|
|`db.data.users`|文件里那个 users 数组|
|`.map(...)`|对每一项做同一件事，返回一个新数组|
|`formatUserData(user, db)`|**去掉密码字段**，顺便把 classId 换成班级名|
|`res.json(...)`|把结果作为 JSON 返回给浏览器|

**`formatUserData` 为什么必须用？**

`db.data.users` 里每一条都带着 `password` 字段。
直接写 `res.json(db.data.users)` 会**把所有人的密码发到浏览器**——
F12 → Network 一看全在。这是很常见的一类泄密，
而且**页面上完全看不出来**，因为页面只显示了名字和头像。

**改哪里**：`backend/routes/users.js` 的 `GET /`，TODO 01 的位置。

**操作前 / 操作后**

- 操作前：照片墙一片空白。
- 操作后：**全班同学的卡片都出现了**，有头像、名字、班级。

**自己验证**
1. 保存后端会自动重启（`npm run dev` 带了 watch），刷新页面。
2. 照片墙出现同学卡片。
3. F12 → Network → `/api/users` 的响应，**搜 `password` 应该搜不到**。
4. **对比实验**：临时把 `formatUserData(user, db)` 改成直接返回 `user`，
   刷新再看响应——**所有人的密码都在里面**。看完改回去。
   这个实验一定要做，它是 TODO 05 的铺垫。

**多想一步**
打开 `backend/db.json` 看一眼。这就是你们的"数据库"——
**一个人人都能用记事本打开的文本文件**，里面的密码是明文。

把这个文件传到任何地方（发给同学、提交进 Git、传到服务器），
所有人的密码就都泄了。所以它在 `.gitignore` 里。
**第 14 课会彻底解决明文密码的问题。**

### TODO 02 · 同一个邮箱不能注册两次

**难度**：简单


**为什么做这个**
邮箱是登录用的身份标识。允许重复的话，登录时**不知道该认哪一个账号**。

**JSON 文件没有任何约束能力**——它就是一段文本，
你写什么它存什么。所以这个检查只能自己写。

**涉及的知识点**

```js
const existingUser = db.data.users.find(user => user.email === email)
if (existingUser) return res.status(400).json({ message: '用户已存在' })
```

`find` 返回第一个满足条件的元素，找不到返回 `undefined`。
`undefined` 在 `if` 里是假值，所以 `if (existingUser)` 就是"找到了"。

**改哪里**：`backend/routes/users.js` 的注册接口，TODO 02 的位置。

**操作前 / 操作后**

- 操作前：同一个邮箱能注册无数次，`db.json` 里出现好几条同邮箱记录。
- 操作后：第二次注册被拒，提示「用户已存在」。

**自己验证**
1. 注册一个账号（比如 `test@abc.com`）。
2. **用同一个邮箱再注册一次** → 被拒。
3. 打开 `backend/db.json` 搜这个邮箱，**只有一条**。

**多想一步（这一条要记住，第 13 课会形成对照）**

你现在写的这段检查有一个**根本性的漏洞**：
如果有别的入口也能写数据（比如另一个接口、一个管理脚本、
或者有人直接编辑 `db.json`），它们**都绕过了这段检查**。

第 13 课换成 SQLite 之后，同样的保护可以写成一句
`email TEXT NOT NULL UNIQUE`——**不管从哪个入口写，都绕不过去**。
那时候代码里这段检查就变成"给人说人话"的角色（把数据库的英文异常
翻译成「用户已存在」），而不是唯一的防线。

**约束保证数据不会错，代码负责给人说人话。** 这句话后面三课会反复出现。

### TODO 03 · 把新用户真正写进文件

**难度**：简单


**为什么做这个**
**这是整个项目 3 的起点问题：数据存在哪，决定了它活多久。**

**涉及的知识点**

```js
db.data.users.push(newUser)   // 只改了内存里的数组
await db.write()              // 把整个对象重新写回文件
```

`push` 改的是**内存**。进程一退出，内存就没了。
`write` 才是把数据落到磁盘上——这一步叫**持久化**。

**改哪里**：`backend/routes/users.js` 的注册接口，TODO 03 的位置。

**操作前 / 操作后**

- 操作前：注册成功、刷新页面还在，但**重启后端就消失**。
- 操作后：重启后端，新用户仍然在。

**自己验证（这个实验一定要按顺序做）**
1. **先不要补那行代码。** 注册一个新账号，刷新页面——他在。
2. **终端 1 按 `Ctrl+C` 停掉后端，再 `npm run dev` 重启**，刷新页面——
   **他不见了。**
3. 打开 `backend/db.json` 搜他的邮箱——**根本没写进去**。
4. 现在补上 `await db.write()`，重复第 1、2 步——**这次他还在**。
5. 再打开 `db.json`，能看到他那一条。

**这个对比是整个项目 3 的起点。** 一定要亲手做一次，不要跳过。

**多想一步**
`db.write()` 是把**整个 `db.json` 重新写一遍**，不是只追加那一条。

这带来两个问题：

|问题|后果|
|---|---|
|数据量大了很慢|43 条无所谓，43 万条每次注册都要重写几十兆|
|两个人同时写会互相覆盖|A 读了全量、B 也读了全量，A 写回、B 再写回——**A 的改动没了**|

第二个问题叫**并发写丢失**，在多人同时用的系统里几乎必然发生。
数据库能解决它（靠事务和行级锁），文本文件不能。
**这是第 13 课换成 SQLite 最根本的理由。**

### TODO 04 · 密码不对不能放行

**难度**：简单


**为什么做这个**
登录是整个系统的入口。

**涉及的知识点**

```js
if (!passwordMatch) return res.status(401).json({ message: '邮箱或密码错误' })
```

注意上面查无此人时的提示语——**和密码错误返回的是同一句话**。

分开提示的话（"该邮箱未注册" / "密码错误"），
攻击者能靠它一个个试出哪些邮箱真实存在，这叫**用户名枚举**。
拿到一批真实邮箱之后，再去撞库就容易多了。
**宁可让正常用户少一点提示，也不给攻击者送信息。**

**改哪里**：`backend/routes/users.js` 的登录接口，TODO 04 的位置。

**操作前 / 操作后**

- 操作前：密码随便填都能登进去。
- 操作后：密码错了提示「邮箱或密码错误」，登不进去。

**自己验证**
1. 用正确密码登录 → 成功。
2. 故意打错密码 → 提示「邮箱或密码错误」，状态码 401。
3. **用一个根本不存在的邮箱登录** → 提示**一模一样**。
4. F12 → Network 对比这两条响应，**应该完全看不出区别**。

**多想一步（这一课最该记住的一件事）**

打开 `backend/db.json`，找到 `password` 字段——**它是明文的**。

这意味着：
- 任何拿到这个文件的人，都拿到了所有人的密码；
- 而很多人在别的网站用的是同一个密码，损失会扩散到你控制不了的地方。

再看看登录接口里那段判断——它是直接拿字符串比对的。

**第 14 课会用 bcrypt 彻底解决这个问题**：
数据库里只存不可逆的摘要，就算被拖库，也还原不出原密码。
**现在先看清楚"不加密是什么样子"，到时候对比才有感觉。**

### TODO 05 · 绝对不能把密码发到前端

**难度**：中等


**为什么做这个**
TODO 01 的对比实验你已经看到了：直接返回数据库里那一行，
**所有人的密码都会发到浏览器**。这一课最后一个任务就是彻底堵住它。

**涉及的知识点：解构赋值剔除字段**

```js
const { password, ...safeUser } = user
```

意思是"把 `password` 单独取出来（然后不用它），**剩下的全部收进 `safeUser`**"。
这是 JavaScript 里剔除字段最简洁的写法。

**为什么不用 `delete user.password`？**

|写法|问题|
|---|---|
|`delete user.password`|**会改动原对象**。而 `user` 还挂在 `db.data.users` 上，改了等于把内存里的数据弄坏了——下次写文件就把密码写没了|
|`const { password, ...safeUser } = user`|**生成一个新对象**，原对象一个字都不动|

**改哪里**：`backend/routes/photowall.js`，TODO 05 的位置。

**操作前 / 操作后**

- 操作前：F12 → Network → 照片墙那条请求的响应里，**每个人都带着密码**。
- 操作后：搜 `password` 搜不到。

**自己验证**
1. F12 → Network → 切换班级 → 找到 `/api/photowall/class/xxx` 那条请求。
2. 看 Response，**搜 `password`，应该搜不到**。
3. 页面上显示的名字、头像、爱好都还在——**只是少了不该给的那一项**。

**多想一步**
把这条当成一个通用习惯：

> **凡是要发给前端的对象，都先想一想：里面有没有不该出去的字段。**

这个项目里是 `password`。真实系统里还可能有身份证号、手机号、
内部备注、审核状态……**默认应该是"只发需要的"，而不是"发全部再删几个"**。

后面三课都会用到同样的思路：第 13 课的 `mapUserRow`、
第 14、15 课的查询语句里只 SELECT 需要的列。

### 已写好 · 班级必须真实存在

**为什么做这个**
用户的 `classId` 指向 `classes` 数组里的某一项。
不检查的话，前端传一个不存在的 id 过来，这个用户就**永远不属于任何班级**——
照片墙按班级筛选时他哪个班都不出现，人却真实存在于数据里。

这种数据叫**孤儿记录**：指向一个不存在的东西。
它很难被发现，因为**页面上看起来一切正常**，只是少了一个人。

**涉及的知识点**

```js
const classExists = (db.data.classes || []).find(c => c.id === classId)
if (!classExists) return res.status(400).json({ message: '所选班级不存在' })
```

注意 `(db.data.classes || [])` 这个写法：
`db.json` 里万一没有 `classes` 这个键，直接 `.find` 会报错。
**读外部文件时，任何一层都可能不存在**，要一层层兜住。

### 已写好 · 照片墙按班级隔离

**为什么做这个**
这是产品本身的需求：群像云图是**按班级**看的，不是把全校混在一起。

**涉及的知识点**

```js
const users = db.data.users
  ? db.data.users.filter(user => user.classId === classId && user.role !== 'admin')
  : []
```

|部分|作用|
|---|---|
|`filter(...)`|只留下满足条件的元素，返回**新数组**|
|`user.classId === classId`|只要这个班的|
|`user.role !== 'admin'`|**排除管理员账号**|
|`db.data.users ? ... : []`|万一 `db.json` 里没有 users 这个键，兜一下|

**为什么要排除管理员？** 管理员是系统账号，不是班上的同学，
出现在照片墙里很奇怪。**这属于产品判断，不是技术问题**——
但它必须在代码里被明确表达出来。

```bat

git log -1 --oneline
```

### 第三步：推送到你自己的仓库

```bat
git push origin main
```

**推送报 `'origin' does not appear to be a git repository` 怎么办？**
本课工程是从教师模板克隆来的，`origin` 已经被改名成 `template`
（那是全班共用的模板仓库，**不能推**）。
先到 GitHub 新建一个空仓库 `p3-nodb-学号`（**不要**勾选 "Add a README file"），然后：

**Windows CMD**

```bat
git remote add origin https://github.com/你的用户名/p3-nodb-学号.git
git branch -M main
git push -u origin main
git remote -v
```

**Windows PowerShell**

```powershell
git remote add origin https://github.com/你的用户名/p3-nodb-学号.git
git branch -M main
git push -u origin main
git remote -v
```

关联一次就够，以后 `git push origin main` 直接能用。
`git remote -v` 应该看到：`origin` 指向你自己的仓库，`template` 指向公共模板仓库。

## 常见问题

### 启动

|现象|原因|处理|
|---|---|---|
|`'npm' 不是内部或外部命令`|Node 没装或没重开终端|装 Node 24，**装完关掉所有终端重开**|
|页面空白，Console 全是请求失败|终端 1 的后端没起来|回终端 1 执行 `npm run dev`|
|`EADDRINUSE`|端口被占用|关掉所有终端重来|
|前端起不来|`frontend` 目录没装依赖|在 `frontend` 里先 `npm install`|
|改了后端代码没生效|watch 没检测到|看终端 1 有没有打印重启；必要时 Ctrl+C 重启|

### 数据

|现象|原因|处理|
|---|---|---|
|**重启后端数据就没了**|TODO 03 没做|补上 `await db.write()`|
|`db.json` 变成空的或坏了|写入过程被打断|从 `backend/db.json.bak` 或 Git 恢复|
|照片墙空白|TODO 01 或 已写好的代码 没做|F12 看 `/api/users` 返回了什么|
|某个人哪个班都不出现|他的 classId 指向不存在的班级|这就是 已写好的代码 要防的孤儿记录|
|页面显示的人数和 db.json 对不上|管理员被排除了|正常现象，见 已写好的代码|

### 接口

|现象|原因|处理|
|---|---|---|
|注册返回 500|`db.json` 结构不对，或字段名拼错|看终端 1 的完整报错|
|curl 发中文乱码|Windows 终端默认不是 UTF-8|用页面测，或把请求体存成 UTF-8 文件再 `-d @req.json`|
|`req.body` 是 undefined|请求没带 `Content-Type: application/json`|curl 要加 `-H "Content-Type: application/json"`|

更多通用排错见 `通用附录_运行提交部署与排错.md`；
命令和参数的逐条解释见 [命令参数逐个拆开](<../../01_入门与通用规范/04_命令参数逐个拆开.md>)。
