## 开课前先讲这三件实测

### 适配器模式，一分钟讲清

这个应用接了五个来源，它们返回的数据**长得完全不一样**：

```text
iTunes   → { trackName, artistName, artworkUrl100, previewUrl }
meting   → { name, artist, pic, url }   或   { title, author, pic, url }
Audius   → { title, user: { name }, artwork: {...} }
```

如果界面里到处写 `if (来源 === 'itunes') ... else if ...`，
**每加一个来源就要翻遍整个项目改一遍**。

适配器的做法：

```text
五种乱七八糟的格式  →  [适配器翻译]  →  一种统一格式  →  界面
```

界面只认最后那一种，**换来源 = 换一个适配器对象，界面一行都不用改**。

打开 `src/adapters/musicAdapter.js` 看最上面那个 `MusicAdapter` 类：
它两个方法都直接抛错。**这是故意的**——谁继承了却忘记实现，
一调用就立刻报错，而不是悄悄返回 `undefined`。

### 这一课要建立的核心观念

> **凡是别人的服务，都要假设它随时会挂。**
> 你的代码好不好，不看它顺利时怎么样，**看它出事时怎么样。**

### TODO 02 · 把两套字段名抹平

**难度**：简单


**为什么做这个**
**这是适配器模式最核心的一下。**

两个 meting 镜像返回的字段名不一样：

```text
api.injahow.cn  →  { name: "屋顶", artist: "周杰伦" }
api.i-meto.com  →  { title: "屋顶", author: "周杰伦" }
```

我们要从**这两个镜像分别拿搜索和播放**（原因见 已写好的代码），
所以必须先把它们统一成一种形状。

**涉及的知识点**

```js
name: raw.name ?? raw.title ?? '未知曲目',
artist: raw.artist ?? raw.author ?? '未知艺术家',
const id = String(url).match(/[?&]id=(\w+)/)?.[1] ?? ''
```

|部分|说明|
|---|---|
|`a ?? b ?? c`|**空值合并可以串起来**：a 没有就用 b，b 也没有就用 c|
|`String(url).match(...)`|从播放地址里**抠出歌曲 id**，已写好的代码 要用它重新拼地址|
|`?.[1]`|可选链：没匹配到时返回 undefined 而不是报错|
|`\w+`|一个或多个"字、数字、下划线"|

**为什么要有兜底值 `'未知曲目'`？**
因为**这是第三方数据，你无法保证它一定有那个字段**。
不兜底的话 `undefined` 会一路流到界面上，用户看到的是空白或者 `undefined`。

**改哪里**：`src/adapters/musicAdapter.js` 的 `MetingAdapter.normalize`，TODO 02 的位置。

- 操作前：搜「周杰伦」，结果**全是「未知曲目 / 未知艺术家」**。
- 操作后：歌名和歌手都正常显示。

### TODO 03 · 音源挂了也不能白屏

**难度**：中等


**为什么做这个**
现在搜「断网」，**整个页面白屏**，Console 里一个未捕获异常。
一个音源出问题就让整个应用不可用，这是不能接受的。

**涉及的知识点**

```js
export async function safeSearch(adapter, keyword, options = {}) {
  try {
    const items = await adapter.search(keyword, options)
    return { items, error: null, source: adapter.constructor.label }
  } catch {
    return {
      items: [],
      error: '这个音源暂时不可用，已经帮你换一个试试',
      retryable: true,
      source: adapter.constructor.label,
    }
  }
}
```

两个设计要点：

1. **返回形状固定。** 不管成功失败，都返回 `{{ items, error, source }}`。
   调用方只要判断 `error` 有没有值，**不用写 try/catch**。
2. **给用户看的是人话。** 不是 `mock_network_error` 这种内部代号——
   **内部代号写进日志给开发者看，提示语写给用户看，两者不是一回事。**

**「断网」这个关键词是什么？**
它是**课堂用的故障开关**：五个适配器里都写了"搜到这两个字就抛错"，
这样不用真的拔网线就能演示故障。**真实项目里当然不会有这种东西**，
但测试环境留一个"可控的失败入口"是很常见的做法。

**改哪里**：`musicAdapter.js` 的 `safeSearch`，TODO 03 的位置。

**操作前 / 操作后**

- 操作前：搜「断网」→ **页面白屏**，Console 红字。
- 操作后：搜「断网」→ **出现一句人话提示**，再搜别的照常能用。

**自己验证**
1. 搜「断网」→ 页面不崩，出提示。
2. **F12 → Console** → **没有红色的未捕获异常**。
3. 接着搜「周杰伦」→ 功能完全正常，**没有留下任何后遗症**。

**多想一步**
注意 `catch { }` 后面没写 `(error)`——这是 ES2019 的**可选 catch 绑定**。

### 已写好 · 给请求加超时

**为什么做这个**

> **公开 API 最常见的故障不是报错，是「一直不回」。**

报错还好办，至少你知道它挂了。**一直不回**的话，
界面上那个"搜索中…"会一直转下去，用户只能刷新页面。

**涉及的知识点**

```js
const controller = new AbortController()
const timer = setTimeout(() => controller.abort(), timeoutMs)
try {
  const response = await fetch(url, { signal: controller.signal })
  ...
} finally {
  clearTimeout(timer)   // ← 这一行最容易漏
}
```

|部分|说明|
|---|---|
|`AbortController`|一个"遥控取消器"|
|`controller.signal`|交给 fetch，fetch 就听它指挥|
|`controller.abort()`|一调，**fetch 立刻抛 `AbortError`**|
|**`finally` 里 `clearTimeout`**|**请求成功也要把定时器清掉**|

**`clearTimeout` 为什么不能少？**
请求 1 秒就成功返回了，但那个定时器还在，**7 秒后它还会触发一次 abort**。
此时 fetch 已经结束不会真出问题，但**定时器堆积起来是实实在在的资源泄漏**。

**用 `finally` 而不是写在 try 末尾**：不管成功、失败还是抛错，`finally` 都一定执行。

**为什么是 8 秒？** 实测：好的镜像 0.5 秒返回，慢的 3 秒。

> **超时时间取决于业务，不是抄来的。**
> 搜索框 1 秒都嫌长，视频转码等 10 分钟都正常。

### 已写好 · 一个镜像挂了就换下一个

**为什么做这个**
**这是整个应用能不能用的关键，也是本课的核心。**

**涉及的知识点**

```js
for (const base of list) {
  try {
    const data = await fetchJson(build(base), options)
    const items = pick(data)
    if (items && items.length) return { items, endpoint: base, failures }
    failures.push({ endpoint: base, reason: '返回空结果' })
  } catch (error) {
    failures.push({ endpoint: base, reason: error.message })
  }
}
```

**只有十几行，但它是"一个服务器挂了另一个顶上"的全部实现。**

两个容易忽略的点：

1. **拿到空结果也算这个镜像没用**，要继续试下一个——
   不是只有抛错才算失败。
2. **失败原因要记进 `failures`**，界面上才能告诉用户"为什么挂了"。

还有一点写在函数末尾：

```js
return { items: [], endpoint: null, failures }
```

**全部失败时不抛错**，而是返回一个正常形状的结果。
调用方不写 try/catch 也不会崩——**错误处理越靠近发生地越好。**

### 第一次部署的时间风险

**这一课的部署是全项目第一次**，要预留够时间：

|卡点|提前说这一句|
|---|---|
|没装 netlify-cli|"先 `npm install -g netlify-cli`，装完**重开终端**"|

## 常见问题

### 搜索

|现象|原因|处理|
|---|---|---|
|结果全是"未知曲目"|TODO 02 没做|`normalize` 要同时认两套字段名|
|搜什么都没有结果|网络不通，或关键词太生僻|切到「课堂合成音」搜「音乐」，能出就说明代码没问题|
|搜「断网」页面白屏|TODO 03 没做|`safeSearch` 要用 try/catch 包住|
|一直转圈不出来|已写好的代码 没做|加超时|
|只有一个音源能用|TODO 04 没做|检查换源顺序|

### 播放

|现象|原因|处理|
|---|---|---|
|点了没声音，Network 里 404|已写好的代码 没做|播放地址要从 play 镜像重新拼|
|点了没反应，也没有请求|浏览器拦了自动播放|点一下播放键即可，第一次需要用户手势|
|有的歌能播有的不能|**公开音源里总有失效的**|这是正常的，第 3 课会做"失效自动跳下一首"|

### 网络

|现象|原因|处理|
|---|---|---|
|所有网络音源都失败|机房网络限制|**课堂合成音一定能用**，本课重点照样能做完|
|封面加载不出来|图片域名被墙或很慢|不影响功能，界面会显示占位符|
|音源状态里全是红点|网络问题|换网络；或者就以此为例讲"这就是为什么要兜底"|
