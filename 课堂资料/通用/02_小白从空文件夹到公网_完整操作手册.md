# 小白从空文件夹到公网：完整操作手册

适用对象：第一次使用 Git、GitHub、终端、CI/CD 或 Ubuntu 服务器的教师与学生。

本手册只走一条主线：

```text
本地文件夹 → 本地 Git 仓库 → GitHub 远程仓库 → CI 检查
→ GitHub Pages / Netlify 公网地址 →（教师）Ubuntu API 与 Nginx
```

第一次操作时，请从第 1 节开始逐项打勾，不要只看命令。以后忘记某一步，再按目录跳转。

本手册命令格式统一如下：命令块可以整块复制到对应终端；以 `#` 开头的是解释性注释，PowerShell 和 Ubuntu Bash 都会忽略。需要姓名、邮箱、仓库名等个人信息时，命令会主动询问，不要求学生修改尖括号占位符。标为“输出示例”的代码块只用于核对，不要执行。

学生第一次领取整套资源，先按 [学生资源领取与 Git 克隆指南](<01_学生资源领取与Git克隆指南.md>) 操作；本手册从个人项目建仓开始。

> 课程约定：P1 主仓库名为 `ffd-p1-portfolio`；静态站主平台为 GitHub Pages、Netlify；Ubuntu 云服务器承载 API；Cloudflare Pages、EdgeOne Pages 为备用平台。SQLite、MySQL 必做，PostgreSQL 备用。P6 选做。

## 0. 先分清六个词

| 名称 | 它是什么 | 本课例子 |
| --- | --- | --- |
| 项目文件夹 | 电脑上实际放代码的目录 | `E:\ffd-student\ffd-p1-portfolio` |
| 本地仓库 | 项目文件夹内含隐藏的 `.git` 目录 | 只有自己电脑看得到 |
| 远程仓库 | GitHub 上保存代码和历史的仓库 | `组织名/ffd-p1-portfolio` |
| commit | 一次有说明的本地存档 | `feat: 完成个人首页` |
| push | 把本地 commit 上传到 GitHub | `git push` |
| deploy | 把代码构建成别人能访问的网站 | Pages 或 Ubuntu |

最容易混淆的一点：`commit` 不等于上传。完成 `commit` 后还要 `push`；完成 `push` 后还要等部署成功，才有公网地址。

## 1. 第一次上机：安装并检查工具

### 1.1 打开 PowerShell

Windows 11：按键盘 `Win`，输入 `PowerShell`，点击“Windows PowerShell”或“终端”。

看到类似下面的提示符就可以输入命令：

```text
PS C:\Users\你的名字>
```

说明：代码框中的命令一行一行执行；不要复制前面的 `PS ...>`；执行一行后按 Enter，等提示符重新出现再执行下一行。

### 1.2 检查 Git、Node.js 和 npm

```powershell
# 显示 Git 版本，确认 Git 已安装并可从终端调用。
git --version
# 显示 Node.js 版本，确认 JavaScript 运行环境已安装。
node --version
# 显示 npm 版本，确认 Node.js 的包管理工具可用。
npm --version
```

<!-- COMMAND_HELP:BEGIN -->
**本段命令怎么读**

`npm` 管理项目依赖并执行脚本；`install` 安装依赖（有兼容的锁文件时使用锁定版本）；`ci` 严格按锁文件安装并重建 node_modules；`run 名称` 执行当前 package.json 的 scripts 中同名命令；`test` 是运行测试脚本。先确认终端所在目录有本课 package.json。服务启动后持续占用终端是正常的，另开终端做下一步，Ctrl+C 才停止服务。

`node` 在终端运行 JavaScript；后接文件路径就是执行该文件；`-v` 只显示版本；`-e` 执行后面引号内的代码；`--check` 只检查语法；`--watch` 监测文件变化并重启。`console.log(...)` 把括号内的结果打印出来，函数调用的参数写在括号里，多个参数用逗号分开。

`git` 管理版本；`status` 查看改动；`diff` 查看逐行差异；`add` 选择待提交文件；`commit -m` 创建本地版本并写说明；`push` 发到远端；`clone` 下载仓库，`--branch` 选择分支，`--single-branch` 只取该分支历史；`remote` 管理远端别名，`fetch` 只取回记录。命令中的 `.` 表示当前目录，`--` 后面是文件路径。推送前用 `git remote -v` 核实 origin 是自己的仓库。
<!-- COMMAND_HELP:END -->


通过标准：三条命令都输出版本号，不出现“无法识别”。课程建议使用环境准备文档指定版本；如果未安装，先按 [环境准备](<03_环境准备.md>) 完成安装，再回到这里。

### 1.3 只做一次：配置提交者姓名和邮箱

整块复制后按提示输入自己的信息：

```powershell
# 读取学生姓名和 GitHub 已验证邮箱；输入内容只保存在本机 Git 配置中。
$gitUserName = Read-Host '请输入你的姓名，例如 张三'
# 读取 GitHub 已验证邮箱。
$gitUserEmail = Read-Host '请输入你的 GitHub 已验证邮箱'
# 设置以后所有本地仓库的 commit 作者姓名。
git config --global user.name $gitUserName
# 设置以后所有本地仓库的 commit 作者邮箱。
git config --global user.email $gitUserEmail
# 统一把新仓库的默认分支命名为 main。
git config --global init.defaultBranch main
```

检查：

```powershell
# 读取刚才保存的提交者姓名。
git config --global user.name
# 读取刚才保存的提交者邮箱。
git config --global user.email
# 确认默认分支名为 main。
git config --global init.defaultBranch
```

姓名可以是中文。邮箱最好使用 GitHub 账号中已验证的邮箱；这两项用于标记 commit，不是 GitHub 登录密码。

## 2. 主路线 A：先在本地创建空仓库，再传到 GitHub

这是第 1 次课推荐路线。下面以 P1 为例，完整做一次。

### 2.1 在磁盘创建课程总文件夹

在 PowerShell 执行：

```powershell
# 在 E 盘创建课程总目录；-Force 表示目录已存在时继续使用，不删除内容。
New-Item -ItemType Directory -Force -Path E:\ffd-student
# 进入课程总目录，后续相对路径都从这里开始。
Set-Location E:\ffd-student
```

<!-- COMMAND_HELP:BEGIN -->
**本段命令怎么读**

`cd` / `Set-Location` 切换终端当前目录；含空格的路径用引号包起来。CMD 的 `/d` 同时切换盘符；PowerShell 用 `Set-Location "路径"`，不加 `/d`。
<!-- COMMAND_HELP:END -->


检查当前位置：

```powershell
# 显示当前所在目录，防止在错误位置创建项目。
Get-Location
```

应包含：

```text
E:\ffd-student
```

如果电脑没有 E 盘，把本手册所有 `E:\ffd-student` 改为 `C:\ffd-student`。

### 2.2 创建 P1 项目文件夹

```powershell
# 创建 P1 项目文件夹；若提示已存在，先停止并核对是否已有作业。
New-Item -ItemType Directory -Path ffd-p1-portfolio
# 进入 P1 项目文件夹，后续 Git 命令都在这里执行。
Set-Location ffd-p1-portfolio
```

再次检查：

```powershell
# 再次显示当前目录，结尾必须是 ffd-p1-portfolio。
Get-Location
```

应为 `E:\ffd-student\ffd-p1-portfolio`。后续 Git 命令都必须在这个目录执行。

### 2.3 把普通文件夹变成本地 Git 仓库

```powershell
# 在当前文件夹创建 .git 本地仓库，并把初始分支命名为 main。
git init -b main
```

正常会看到类似：

```text
Initialized empty Git repository in E:/ffd-student/ffd-p1-portfolio/.git/
```

检查仓库根目录：

```powershell
# 显示当前仓库根目录，确认没有误在上一级目录初始化。
git rev-parse --show-toplevel
# 显示当前分支，预期输出 main。
git branch --show-current
```

第一条应指向本项目目录；第二条应显示 `main`。`.git` 是隐藏目录，不需要打开或修改。

### 2.4 用 VS Code 打开当前目录

```powershell
# 用 VS Code 打开当前项目目录；句点表示“当前目录”。
code .
```

如果 `code` 无法识别：打开 VS Code，点击“文件 → 打开文件夹”，选择 `E:\ffd-student\ffd-p1-portfolio`。

在 VS Code 左侧文件区依次创建：

- `README.md`：输入 `# P1 一页知我`；
- `index.html`：输入最小 HTML，或复制第 1 次课 starter 中的对应文件；
- `.gitignore`：逐行输入 `node_modules/`、`dist/`、`.env`、`*.sqlite`。

按 `Ctrl+S` 保存每个文件。不要把整个 starter 文件夹再套一层复制进项目；最终应直接看到 `项目目录/index.html`，而不是 `项目目录/starter/index.html`。

### 2.5 看清 Git 的三个状态

```powershell
# 查看未跟踪、已修改和已暂存文件；此命令只读，不修改文件。
git status
```

第一次应在 `Untracked files` 下看到新文件，意思是“Git 还未跟踪”。

把文件放入本次提交的暂存区：

```powershell
# 只把这三个明确文件加入暂存区，避免误提交密钥或 node_modules。
git add README.md index.html .gitignore
# 再看状态，三个文件应出现在 Changes to be committed 下。
git status
```

此时文件应出现在 `Changes to be committed` 下，通常为绿色，意思是“已经选入下一次 commit”。

如果放错文件，可安全取消暂存，不会删除文件：

```powershell
# 询问要取消暂存的文件名，例如 index.html；不会删除文件内容。
$stagedFile = Read-Host '请输入要取消暂存的文件名'
# 只把该文件移出暂存区，文件仍保留在磁盘。
git restore --staged -- $stagedFile
```

### 2.6 创建第一次本地提交

```powershell
# 把暂存区内容保存为第一次本地提交；-m 后面是本次修改说明。
git commit -m "feat: 创建P1个人首页"
```

正常会看到类似：

```text
[main (root-commit) abc1234] feat: 创建P1个人首页
 3 files changed, ...
```

检查提交历史：

```powershell
# 用单行格式显示最近 5 次提交，确认刚才的 commit 已产生。
git log --oneline -5
# 确认当前没有遗漏的未提交修改。
git status
```

应看到刚才的说明，并看到 `nothing to commit, working tree clean`。这表示本地存档成功，尚未上传。

### 2.7 在 GitHub 网页创建“真正的空仓库”

1. 浏览器登录 GitHub，打开 <https://github.com/new>。
2. `Owner`：教师建设仓库时选课程组织；学生没有组织建仓权限时选自己的 GitHub 用户名。
3. `Repository name`：输入 `ffd-p1-portfolio`。学生重名时可按教师规定加学号，例如 `ffd-p1-portfolio-20260001`。
4. `Description`：可填 `前端框架应用开发 P1`。
5. 教师要求公开部署时选 `Public`。
6. **不要勾选** `Add a README file`。
7. `.gitignore template` 保持 `None`。
8. `License` 保持 `None`。
9. 点击 `Create repository`。

为什么三个初始化选项都不选：本地已经有第一次 commit；网页再生成 README 会形成两条不同历史，给第一次操作增加冲突。

### 2.8 连接本地仓库与 GitHub 仓库

创建后停留在 GitHub 的 `Quick setup` 页面，点击 `HTTPS`，复制以 `.git` 结尾的地址。

课程组织地址示例（这是地址示例，不执行）：

```text
https://github.com/02-gdit-ffd-20260818/ffd-p1-portfolio.git
```

回到**仍位于项目目录**的 PowerShell。整块复制并按提示输入 GitHub 用户名：

```powershell
# 读取学生自己的 GitHub 用户名并组成远程仓库地址。
$githubUser = Read-Host '请输入你的 GitHub 用户名'
# 根据用户名生成 P1 远程仓库 HTTPS 地址。
$remoteUrl = "https://github.com/$githubUser/ffd-p1-portfolio.git"
# 把远程仓库登记为 origin。
git remote add origin $remoteUrl
# 显示下载和上传地址，确认两行地址都正确。
git remote -v
```

应出现两行 `origin`，分别标有 `(fetch)` 和 `(push)`，地址与网页一致。

### 2.9 第一次上传

```powershell
# 把本地 main 首次上传到 origin，并建立以后默认的跟踪关系。
git push -u origin main
```

第一次可能弹出浏览器或 Git Credential Manager：

1. 选择 `Sign in with your browser`；
2. 登录拥有该仓库权限的 GitHub 账号；
3. 点击授权；
4. 返回 PowerShell 等待完成。

不要在聊天、截图、代码或 `.env` 中发送密码、Token、私钥。GitHub 网页密码不能直接当作 Git 命令密码。

成功末尾通常包含：

```text
branch 'main' set up to track 'origin/main'
```

刷新 GitHub 仓库网页，应看到 `README.md`、`index.html` 和第一次提交说明。再检查：

```powershell
# 查看工作区是否干净以及当前分支状态。
git status
# 再次核对远程地址，避免上传到错误账号。
git remote -v
```

到这里才完成“本地建仓 → 本地提交 → 上传远程仓库”。

## 3. 路线 B：先在 GitHub 建空仓库，再克隆到本地

只有在本地尚无项目文件时使用这条路线。

1. 按 2.7 创建仓库。本路线可以勾选 README，但课程统一操作时仍建议不勾选。
2. 在仓库网页点击绿色 `Code` → `Local` → `HTTPS` → 复制地址。
3. 打开 PowerShell：

```powershell
# 进入课程总目录，clone 会在这里创建项目文件夹。
Set-Location E:\ffd-student
# 询问 GitHub 用户名并生成仓库地址。
$githubUser = Read-Host '请输入你的 GitHub 用户名'
# 根据用户名生成要克隆的 P1 HTTPS 地址。
$remoteUrl = "https://github.com/$githubUser/ffd-p1-portfolio.git"
# 下载远程仓库及其完整 Git 历史。
git clone $remoteUrl
# 进入刚克隆的项目目录。
Set-Location ffd-p1-portfolio
# 显示远程地址，确认 clone 来源正确。
git remote -v
```

4. 将 starter **里面的文件**复制到当前项目目录，不复制 starter 自身的 `.git`。
5. 执行：

```powershell
# 查看复制 Starter 后有哪些新文件或修改。
git status
# 本步骤用于首次导入 Starter；执行前必须确认没有 .env、数据库、node_modules 或 solution。
git add .
# 把首次起点保存为本地提交。
git commit -m "feat: 完成第1次课起点"
# 上传到当前分支对应的 GitHub 远程分支。
git push
```

不要把 A、B 两条路线混在一起。判断自己是否已经在仓库内：

```powershell
# 显示当前仓库根目录；若报 fatal，说明尚未进入项目目录。
git rev-parse --show-toplevel
```

若输出 `fatal: not a git repository`，说明当前目录不对；先 `Set-Location` 进入项目目录。若输出的是上一级大目录，说明可能误在外层执行过 `git init`，停止操作并请教师检查，避免创建嵌套仓库。

## 4. 以后每次课都重复的 Git 工作流

### 4.1 上课开始：先同步并建分支

```powershell
# 进入个人 P1 仓库；其他项目请把最后的目录名改为对应仓库名。
Set-Location E:\ffd-student\ffd-p1-portfolio
# 切换到主分支。
git switch main
# 只接受快进更新，从 GitHub 同步最新 main；出现分叉时停止而不自动合并。
git pull --ff-only
# 从当前 main 创建并切换到第 2 课个人分支。
git switch -c lesson-02-responsive
```

分支名按本课任务改写，例如 `lesson-09-api`。如果提示分支已存在：

```powershell
# 已存在该分支时直接切换，不再重复创建。
git switch lesson-02-responsive
```

### 4.2 编码过程中：小步提交

完成一个可说明的小功能后：

```powershell
# 查看哪些文件发生变化。
git status
# 查看尚未暂存的逐行差异。
git diff
# 交互输入本次确实要提交的文件，例如 src/App.vue。
$changedFile = Read-Host '请输入本次要暂存的具体文件路径'
# 只暂存这个文件。
git add -- $changedFile
# 再看状态，确认暂存区没有秘密和无关文件。
git status
# 用明确说明保存本次本地提交。
git commit -m "feat: 增加移动端导航"
# 首次上传本课分支并建立跟踪关系。
git push -u origin lesson-02-responsive
```

推荐提交说明：`feat:` 新功能，`fix:` 修复，`docs:` 文档，`test:` 测试，`chore:` 配置维护。

不要机械执行 `git add .`。先看 `git status`，确认其中没有 `.env`、数据库、密钥、`node_modules` 或教师 solution。

### 4.3 在 GitHub 创建 Pull Request

1. 打开仓库网页；通常会出现黄色提示条，点击 `Compare & pull request`。
2. `base` 选 `main`，`compare` 选本课分支。
3. 标题写清本课成果，例如 `第2次课：响应式个人首页`。
4. 正文填写：完成项、测试命令、可访问地址、已知问题。
5. 点击 `Create pull request`。
6. 等页面底部 CI 检查全部绿色。红色时点开 `Details`，找到第一条真正的错误。
7. 教师/同伴审核通过后点击 `Merge pull request` → `Confirm merge`。
8. 回到本地同步：

```powershell
# PR 合并后切回本地主分支。
git switch main
# 下载远程已合并的最新内容，只允许快进。
git pull --ff-only
# 显示最近 5 次提交，确认合并结果已经同步。
git log --oneline -5
```

### 4.4 每次课下课前必须交的五项证据

- GitHub 仓库或 PR 地址；
- 本课 commit 短编号：`git rev-parse --short HEAD`；
- 本地测试通过截图或文字；
- GitHub Actions 绿色运行地址；
- 公网可访问 URL，并用无痕窗口再打开一次。

## 5. Node/Vite 项目如何在本地运行

进入含 `package.json` 的目录：

```powershell
# 按 package-lock.json 精确安装依赖，保证全班依赖版本一致。
npm ci
# 启动 Vite 开发服务器；终端保持运行属于正常现象。
npm run dev
```

终端会显示 `Local: http://localhost:...`。按住 `Ctrl` 点击地址，或复制到浏览器。运行期间终端不会回到提示符，这是正常的；结束时在终端按 `Ctrl+C`，出现询问则输入 `Y`。

提交前运行（以项目 `package.json` 实际脚本为准）：

```powershell
# 运行项目定义的自动测试。
npm test
# 生成生产构建，成功后通常得到 dist 目录。
npm run build
# 检查测试和构建是否产生不应提交的文件。
git status
```

`npm ci` 要求仓库内有 `package-lock.json`。若 starter 第一次尚未生成锁文件，按其 `START_HERE.md` 执行一次 `npm install`，随后提交锁文件。不要提交 `node_modules` 和 `dist`。

## 6. GitHub Pages：P1 的第一条自动部署链

### 6.1 先确认仓库具备工作流

仓库应有 `.github/workflows/` 下的 Pages 工作流。课程可复制 [CI-CD 与部署配置](<05_CI-CD与部署配置.md>) 第 9.1 节的静态站工作流，但要按项目实际脚本和目录核对。推送后打开仓库 `Actions` 标签，应看到一次运行。

### 6.2 第一次启用 Pages

1. 打开仓库 → `Settings`。看不到时，检查自己是否有管理员权限。
2. 左侧 `Code and automation` → `Pages`。
3. `Build and deployment` 的 `Source` 选择 `GitHub Actions`。
4. 回到 `Actions`，点最新工作流；黄点表示运行中，绿勾表示成功，红叉表示失败。
5. 成功后回到 `Settings → Pages` 查看网址。

组织仓库 P1 示例：<https://02-gdit-ffd-20260818.github.io/ffd-p1-portfolio/>。

### 6.3 验收自动部署

修改首页一个可见文字，完成 `add → commit → push`。不在 Pages 网页手动上传。观察 Actions 变绿，再用无痕窗口打开公网 URL，必须看到新文字。

下面的命令会主动询问本次修改的文件，整块复制：

```powershell
# 先查看修改范围，确认当前位于正确项目和分支。
git status
# 显示尚未暂存的具体差异。
git diff
# 输入刚才修改的文件，例如 index.html 或 src/App.vue。
$deployFile = Read-Host '请输入本次修改的文件路径'
# 只暂存指定文件并创建部署提交。
git add -- $deployFile
# 为本次 Pages 验收变化创建提交。
git commit -m "docs: 更新Pages验收文字"
# 把当前分支提交上传到 GitHub，触发 Actions 和 Pages。
git push
```

如果 Actions 绿但页面旧：先等待 1—3 分钟，再强制刷新 `Ctrl+F5`；仍旧时核对访问 URL、分支和 commit 是否一致。

## 7. Netlify：P3/P4/P5 的主部署方法

1. 先在本地执行下面命令；确认生成 `dist`。

```powershell
# 根据锁文件精确安装依赖。
npm ci
# 运行自动测试，失败时先修复，不进入部署。
npm test
# 生成 Netlify 将要发布的生产文件。
npm run build
# 确认 dist 目录已经生成并包含文件。
Get-ChildItem -LiteralPath .\dist
```

2. 登录 Netlify，进入团队的 `Projects` 页面。
3. 点击 `Add new project` → `Import an existing project`。
4. 选择 `GitHub` 并授权。组织仓库看不到时，在授权页给 Netlify GitHub App 增加该组织/仓库访问权限。
5. 选择仓库。
6. `Branch to deploy` 选 `main`。
7. 普通 Vite 项目填写：`Build command` 为 `npm run build`，`Publish directory` 为 `dist`。若项目文档写了其他值，以项目为准。
8. 有子目录时，`Base directory` 填真正含 `package.json` 的目录；根目录项目留空。
9. 点击 `Publish`/`Deploy`，等待部署日志完成。
10. 打开 Netlify 提供的 `*.netlify.app` 地址，用无痕窗口验收。

后续只需向 GitHub `main` 推送，Netlify 会自动重新构建。部署失败时进入该项目的 `Deploys` → 最新失败记录，先找日志中第一条 `Error`，不要只截图最后一行。

环境变量在 Netlify 项目设置的 `Environment variables` 中配置；只填变量值，不把生产 `.env` 上传 GitHub。前端 `VITE_` 变量会进入浏览器构建产物，不能放秘密。

## 9. CI 红了怎么查：只看第一处真正错误

1. 本地先整块运行与 CI 相同的命令：

```powershell
# 清洁安装依赖；这里失败通常表示锁文件或 Node 版本问题。
npm ci
# 运行项目测试；先处理输出中的第一条失败断言。
npm test
# 运行生产构建；先处理输出中的第一条 Error。
npm run build
```

2. 打开 GitHub 仓库 → `Actions` → 红叉运行 → 红叉 job → 展开失败 step。
3. 从上往下找第一行 `Error` 或 `failed`；末尾 `Process completed with exit code 1` 只是结果。
4. 在本地修复，重新运行；通过后再 `add → commit → push`。不要在网页上“强行变绿”。

常见原因：忘交 `package-lock.json`、文件名大小写不同、脚本名不一致、测试数据缺失、Node 版本不同、构建环境变量未配置。

## 10. Git 常见报错对照表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `not a git repository` | 当前目录不是仓库 | `Get-Location`，再 `Set-Location` 到项目目录 |
| `Author identity unknown` | 未配置姓名邮箱 | 回到 1.3 执行两条 `git config` |
| `remote origin already exists` | 已经加过远程 | 先 `git remote -v`；地址错才执行 `git remote set-url origin 正确地址` |
| `repository not found` | 地址错或账号无权限 | 核对浏览器账号、Owner、仓库名和授权 |
| `rejected ... fetch first` | 远程有本地没有的提交 | 停止重复 push；先 `git pull --rebase origin main`，冲突时请教师协助 |
| `nothing to commit` | 没有新改动或未保存 | `git status`，回编辑器 `Ctrl+S` |
| `src refspec main does not match` | 还没有第一次 commit | 完成 2.5—2.6 后再 push |
| 网页没有新代码 | 只 commit 未 push，或推错分支 | `git status -sb`、`git branch --show-current`、`git push` |
| `npm` 无法识别 | Node.js 未安装或终端未重开 | 按环境准备安装，关闭并重开终端 |

不要执行网上随手复制的 `git reset --hard`、`git clean -fd` 或递归删除命令。先保存工作副本并让教师判断。

## 11. 教师专用：Ubuntu 服务器先看懂再操作

学生完成课程不需要服务器 root 权限。以下步骤仅由任课教师在维护窗口执行。

### 11.1 当前服务器结构（2026-09-07 已核对）

| 项目 | 公网入口 | 内部服务 | systemd | 程序目录 |
| --- | --- | --- | --- | --- |
| P2 | `http://47.120.73.69/ffd-p2-api/` | 3010 | `ffd-p2-api` | `/srv/ffd-p2/app` |
| P3 | `http://47.120.73.69/ffd-p3-api/` | 3020 | `ffd-p3-api` | `/srv/ffd-p3/current` |
| P4 | `http://47.120.73.69/ffd-p4-api/` | 3030 | `ffd-p4-api` | `/srv/ffd-p4/current` |

Nginx 监听公网 80，再把三个路径转发给内部 Node 服务。公网实测 3010/3020/3030 不可直连；云平台安全组应继续只放行管理所需 SSH 端口和 Web 端口，不要开放三个内部端口。

P2 数据和备份位于 `/srv/ffd-p2/data`、`/srv/ffd-p2/backups`。P3/P4 的 `current` 是指向 `/srv/ffd-p3/releases/...`、`/srv/ffd-p4/releases/...` 的软链接，便于切换版本。

### 11.2 从 Windows 登录服务器

打开 PowerShell：

```powershell
# 使用已经安装的 SSH 客户端，以 root 用户连接指定服务器。
# 学生不要执行；仅限持有已授权公钥的任课教师。
ssh root@47.120.73.69
```

第一次会询问主机指纹。先与教师交接记录核对 IP/指纹，确认后输入 `yes`。公钥已安装时不会询问 root 密码。成功提示符类似：

```text
root@服务器名:~#
```

退出服务器：

```bash
# 安全结束当前 SSH 会话并返回 Windows PowerShell。
exit
```

判断自己在哪里：出现 `PS C:\...>` 是本地 Windows；出现 `root@...#` 是服务器。不要把 PowerShell 命令输进 Ubuntu，也不要把服务器命令输到 Windows。

### 11.3 每次上课前只做只读体检

登录服务器后逐行执行：

```bash
# 只读检查 Nginx 和三个 API 服务是否为 active，不会重启服务。
systemctl is-active nginx ffd-p2-api ffd-p3-api ffd-p4-api
# 检查 Nginx 配置语法；此命令不会应用配置。
nginx -t
# 分别访问三个 Node 服务的内部 health，定位应用层是否正常。
curl -fsS http://127.0.0.1:3010/health
# 访问 P3 内部 health。
curl -fsS http://127.0.0.1:3020/health
# 访问 P4 内部 health。
curl -fsS http://127.0.0.1:3030/health
# 通过 Nginx 的本机入口访问三个 health，验证反向代理路径。
curl -fsS http://127.0.0.1/ffd-p2-api/health
# 通过 Nginx 访问 P3 health。
curl -fsS http://127.0.0.1/ffd-p3-api/health
# 通过 Nginx 访问 P4 health。
curl -fsS http://127.0.0.1/ffd-p4-api/health
```

`systemctl` 四行应为 `active`；`nginx -t` 应出现 syntax is ok / test is successful；`curl` 应返回健康 JSON。再从本地浏览器检查公网 URL，才算体检通过。

### 11.4 服务异常时按层定位

先看状态，不要先重启：

```bash
# 显示 P2 服务当前状态和最近错误摘要，不重启服务。
systemctl status ffd-p2-api --no-pager -l
# 显示 P2 服务最近 15 分钟日志；只读，不修改服务。
journalctl -u ffd-p2-api --since '-15 min' --no-pager
```

把服务名替换为 P3/P4 即可。判断：

- 内部 `127.0.0.1:端口/health` 失败：查 Node 服务、环境变量、数据库和日志；
- 内部成功，但 `127.0.0.1/ffd-pX-api/health` 失败：查 Nginx 配置和日志；
- 服务器本机成功，但公网失败：查云安全组、域名/DNS、证书或网络；
- 只有前端页面请求失败：查前端 API 基址、CORS 和 HTTPS 混合内容。

确认配置正确后才可重启单个服务：

```bash
# 只重启已经确认需要恢复的 P2 服务。
systemctl restart ffd-p2-api
# 确认重启后服务状态回到 active。
systemctl is-active ffd-p2-api
# 验证应用内部 health。
curl -fsS http://127.0.0.1:3010/health
# 验证经 Nginx 转发的 health。
curl -fsS http://127.0.0.1/ffd-p2-api/health
```

不要无原因重启全部服务。

### 11.5 Nginx 修改规则

修改前先备份目标配置文件；修改后必须按顺序：

```bash
# 修改 Nginx 文件后先做语法检查；失败时下面两条不应执行。
nginx -t
# 仅重新加载 Nginx 配置，不中断已有连接。
systemctl reload nginx
# 确认重新加载后 Nginx 仍为 active。
systemctl is-active nginx
```

若 `nginx -t` 失败，不执行 reload，根据它给出的文件名和行号修正。没有自有域名时继续使用当前 HTTP/IP；取得域名后按 [项目 3 的 Ubuntu 部署教程](../关联资料/02_教学资源包/04_项目3_群像云图_完整课堂包/PersonaLink_Docker/docs/deploy-ubuntu.md)中的 Certbot 一节 操作。

### 11.6 发布新后端前的不可跳过清单

1. GitHub CI 已绿，记录待发布 commit：`git rev-parse HEAD`。
2. 阅读该 solution 的 `docs/deployment-runbook.md`；不同项目的迁移命令不可混用。
3. 备份数据库，并在隔离库做过恢复验证。
4. 记录当前版本：服务器执行 `readlink -f /srv/ffd-p3/current` 或记录 P2 当前 commit。
5. 新代码先放新 release/incoming 目录，绝不覆盖数据库、`/etc/ffd-pX-api.env` 或备份目录。
6. 在新目录安装依赖、迁移、验证，再切换 `current` 或按 P2 runbook 更新。
7. 只重启目标服务，连续检查内部 health、Nginx health、公网 health 和核心业务请求。
8. 任一验收失败立即回滚上一 release/备份，不在生产机边猜边改。

P3/P4 的标准回滚思路（`上一版本目录` 必须先通过 `ls` 确认真正存在）：

```bash
# 列出 P3 已有发布目录。教师先从输出中人工确认上一版本确实存在。
ls -ld /srv/ffd-p3/releases/*
# 显示 current 当前指向的真实目录，记录回滚前版本。
readlink -f /srv/ffd-p3/current
# 交互输入已经从 ls 输出中确认的上一版本目录名。
read -r -p '请输入已确认的上一版本目录名：' previous_release
# 验证目标目录存在；不存在就停止，不改变 current。
test -d "/srv/ffd-p3/releases/$previous_release" || { echo '目标目录不存在，已停止'; exit 1; }
# 将 current 软链接切换到确认存在的上一版本。
ln -sfn "/srv/ffd-p3/releases/$previous_release" /srv/ffd-p3/current
# 只重启 P3 服务，使它读取回滚版本。
systemctl restart ffd-p3-api
# 验证 P3 应用内部 health。
curl -fsS http://127.0.0.1:3020/health
# 验证 P3 经 Nginx 的 health。
curl -fsS http://127.0.0.1/ffd-p3-api/health
```

这里故意不提供可直接粘贴的“通用一键发布命令”：P2、P3、P4 的目录、数据库迁移和回滚对象不同。教师发布时必须打开目标项目自己的 runbook 逐项签字。

## 12. SQLite、MySQL、PostgreSQL 到底怎么用

| 数据库 | 课程定位 | 新手必须知道 |
| --- | --- | --- |
| SQLite | 必做，先理解持久化 | 是一个文件；不能放进 Git；发布代码时不能覆盖；备份是复制/项目脚本并验证恢复 |
| MySQL | 必做，生产主链 | 密码只放服务器环境文件/GitHub Secrets；迁移、seed、backup、restore 都用项目脚本 |
| PostgreSQL | 备用 | 不自动替换生产 MySQL；只有完整演练通过后才在维护窗口切换 |

本地课堂先使用 starter 文档规定的测试库。服务器环境变量位于 `/etc/ffd-p2-api.env` 等文件，不得复制进学生包、GitHub 或截图。查看环境变量**名称**可以，公开环境变量**值**不可以。

数据库恢复是破坏性操作。固定顺序：备份当前库 → 记录条数 → 恢复到临时隔离库 → 核对表和条数 → 维护窗口停服务 → 再决定是否恢复生产 → health 与业务验收。未完成隔离恢复验证，不操作生产库。
