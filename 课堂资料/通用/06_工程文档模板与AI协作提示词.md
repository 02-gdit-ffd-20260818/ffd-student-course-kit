# 工程文档模板与 AI 协作提示词

> 本文件是**跨课通用**的，不属于任何一个项目。
> 十八次课里凡是要写 Issue、写 PR、记测试、做部署记录、用 AI 助手的地方，都回到这一页复制。
>
> 每一课的《课堂操作手册》末尾还有一张「本课交付清单」，那是**单次课**的要求；
> 这一页是**跨课通用**的底线。两者都要满足。

## 一、什么时候用哪一份

|要做的事|用下面第几节|什么时候写|
|---|---|---|
|记录一个待办：要做什么、怎么算做完|2.1 Issue|**动手写代码之前**|
|说明这次改动做了什么、怎么验证的|2.2 Pull Request|提交或合并之前|
|正常、边界、失败三类测试的实际结果|2.3 测试记录|每次课的验证环节|
|部署步骤、回滚步骤、健康检查|2.4 部署 Runbook|项目 3 第 14、15 课；项目 4 第 3 课上线时|
|这一版改了什么、已知问题是什么|2.5 Release Note|打版本标签时|
|为什么选这个方案、放弃了什么|2.6 ADR|做出有取舍的技术选择时|
|用 AI 助手做了什么、采纳或拒绝的理由|2.7 Agent 日志|**每次使用 Agent 之后**|
|向 AI 提问|第三节的六条提示词|按需求 → 实现 → 测试 → 排错 → 审查 → 发布的顺序|

## 二、工程文档模板

学生写工程文档时直接复制下面的模板，不用从空白页开始。教师批改时也按这些字段看。

### 三条使用原则

1. **先写 Issue 再写代码。** 说不清要做什么、怎么算做完，就还不到动手的时候。
2. **ADR 记的是取舍，不是结论。** "为什么不选另一个方案"往往比"选了什么"更值得写。
3. **Agent 日志要写拒绝的部分。** 只记"AI 帮我写了什么"没有意义，
   记下"哪一段我没采纳、因为什么"才说明你真的看懂了。

---

### 2.1 Issue 模板

> 放到仓库的 `.github/ISSUE_TEMPLATE/` 下，GitHub 新建 Issue 时会自动套用。

```markdown
---
name: 功能/缺陷任务
about: 一次课可完成、可验收、可发布的最小任务
---
## 用户故事
作为[用户]，我希望[完成任务]，从而[获得价值]。

## 本次范围 / 非目标

## 验收标准
- [ ] Given ... When ... Then ...

## 测试
- [ ] 正常
- [ ] 边界
- [ ] 失败

## 风险/依赖

## 完成证据
URL / commit / CI / Release：
```

**「非目标」这一栏经常被跳过，但它最有用**——写清楚"这次不做什么"，
才不会做着做着范围越滚越大，最后一次课交不出东西。

---

### 2.2 Pull Request 模板

> 放到仓库根目录或 `.github/` 下，文件名 `pull_request_template.md`。

```markdown
## 关联 Issue
Closes #

## 改了什么 / 为什么

## 自检
- [ ] 验收标准通过
- [ ] 正常/边界/失败测试有记录
- [ ] lint/test/build 通过
- [ ] 无密钥和隐私数据
- [ ] README/CHANGELOG/.env.example 按需更新

## 截图、URL、CI

## 风险与回滚

## Agent 参与与本人审查
```

---

### 2.3 测试记录

```markdown
# 测试记录

| 编号 | 类型 | 前置条件 | 步骤 | 期望 | 实际 | 结果 | 证据 |
|---|---|---|---|---|---|---|---|
| T01 | 正常 | | | | | | |
| T02 | 边界 | | | | | | |
| T03 | 失败 | | | | | | |
```

**三种类型缺一不可。** 只测正常路径等于没测——
真实故障几乎都发生在边界（空值、超长、0、并发）和失败路径（网络断、对方返回错误）上。

---

### 2.4 部署与恢复 Runbook

```markdown
# 部署与恢复 Runbook

## 环境与入口
仓库 / CI / 生产 URL / 健康检查：

## 发布步骤

## 环境变量（只写名称，不写值）

## 日志位置

## 数据备份

## 回滚步骤

## 从 Tag + 配置 + 备份恢复

## 最近一次演练结果
```

**最后一栏是这份文档的灵魂。**
没有演练过的恢复步骤，等于没有恢复步骤——
项目 3 第 13、14、15 课都要求实际演练一次并把结果写在这里。

---

### 2.5 Release Note

```markdown
# Release vX.Y.Z

发布日期：
线上地址：
对应 Tag/commit：

## 用户可见变化

## 修复问题

## 测试与 CI

## 部署/数据库变更

## 已知问题与回滚方法

## 下一版
```

**「用户可见变化」要用用户的话写**，不要写"重构了 service 层"。
用户不关心你怎么改的，只关心他能感觉到什么。

---

### 2.6 ADR（架构决策记录）

```markdown
# ADR-XXX：决策标题

状态：提议/接受/废弃　日期：

## 背景与约束

## 候选方案

## 决策与理由

## 后果、风险与撤销条件
```

**「撤销条件」是最容易漏也最值得写的一栏**：
什么情况下我们要推翻这个决定？把它写下来，将来就不用靠吵架来决定。

本课程里天然适合写 ADR 的地方：
项目 3 选 SQLite 还是 MySQL；项目 4 选 Serverless 还是自己搭服务器；
项目 5 的音源接入方式。

---

### 2.7 Agent 协作记录

```markdown
# Agent 协作记录

任务 / 上下文：
采用的建议及理由：
拒绝的建议及理由：
关键 diff：
测试结果：
风险与下一步：
本人能解释的关键代码：
```

**最后一栏是答辩时的硬条件**——
第 18 课工程答辩要求现场解释关键代码，解释不了的按硬性规则处理。

## 三、AI 协作提示词

**使用顺序**：需求澄清 → 实施单个 Issue → 测试设计 → 故障定位 → 代码审查 → 发布与复盘。

**两条纪律**：

- 提示词里的方括号内容由学生自己替换；
- **不得粘贴密钥、账号或真实隐私数据**——
  你发给 AI 的内容，等于发给了一个你无法控制的第三方服务。

---

### 3.1 需求澄清与验收

```text
你是软件需求分析搭档。基于以下真实用户与场景，先指出信息缺口，
再把需求压缩为一节课可发布的最小垂直切片。
输出：1 条 User Story、非目标、2—4 条可观察验收标准、
正常/边界/失败测试各 1 条、风险和需向用户确认的问题。不要写代码。

用户与场景：[填写]
当前版本与仓库状态：[填写]
本次想解决的问题：[填写]
时间约束：[填写]
```

**「先指出信息缺口」这一句很关键**——
它逼 AI 先承认不知道什么，而不是靠猜把空补满。

---

### 3.2 实施单个 Issue

```text
请先阅读我提供的 Issue、验收标准、目录结构和相关文件。
先输出不超过 6 步的实施计划、会修改的文件和主要风险；等我确认后再给出最小 diff。
只修改本 Issue 必需内容，不新增框架，不改无关样式，不读取或输出密钥。
完成后列出运行命令、测试结果、仍存在的风险和建议 commit message。
```

**「等我确认后再给出 diff」是这条提示词的价值所在。**
让它先说计划，你能在它动手之前发现方向错了——改计划比改代码便宜得多。

---

### 3.3 测试设计

```text
根据用户故事、验收标准和当前实现，生成一个最小测试矩阵：
正常、边界、失败、权限/安全、回归。
每条包含前置条件、步骤、期望结果、自动/手工类型和优先级。
优先覆盖会阻止发布的风险，不追求数量。
```

---

### 3.4 故障定位

```text
请不要直接猜修复。根据错误信息、复现步骤、控制台/Network/服务器日志和最近 diff：
先建立 3 个最可能假设，给出区分它们的最小检查；
找到根因后给最小修复、回归测试和预防措施。
若证据不足，明确需要什么日志。
```

**「不要直接猜修复」和「建立 3 个假设」是这条提示词的全部意义。**
直接给一个修复，你不知道它对不对；
给三个假设和区分它们的方法，你能自己验证——**而且你学会了怎么查。**

---

### 3.5 代码审查

```text
请以 Reviewer 身份审查以下 diff。按严重程度列出：阻断合并、建议修复、可选改进。
重点检查验收标准、可维护性、重复代码、异常状态、可访问性、安全/隐私、密钥、
性能和测试缺口。
每条必须引用具体文件/函数并给出最小修复建议；不要重写整个项目。
```

---

### 3.6 发布与复盘

```text
根据本次 Issue、diff、测试、CI 日志和部署结果，生成：
语义化版本建议、Release Note、部署前检查、部署后 smoke test、
回滚条件、已知问题、用户可见变化和下一版 Backlog。
不要声称未提供证据的测试已经通过。
```

**最后一句是防止 AI 编造结果。** 它很擅长写出"测试全部通过"这种话，
哪怕你根本没给它任何测试输出。
